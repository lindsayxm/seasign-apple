## Goal

Plan plans/2026-11-19-google-calendar-push.md, task A. The app will send a short-lived Google OAuth access token in the X-Google-Token header; the Worker calls the Google Calendar API and answers in the same event shape as /v1/calendar/events. Local only; nothing is deployed.

## Acceptance criteria

- [x] GET /v1/google/calendars (header X-Google-Token): the user's calendars from calendarList.list as id, name, primary flag, colour if cheap. POST /v1/google/events (header X-Google-Token; body: calendar ids (max 10) and timezone): events that have not ended and start within the next 7 days, soonest first, at most 50, with the same event fields and all-day handling as /v1/calendar/events, using events.list with singleEvents=true, orderBy=startTime, timeMin/timeMax; cancelled events left out; a per-calendar ok/error status like the existing route
- [x] Look up the current Google Calendar API reference (events.list, calendarList.list, error bodies) before writing; do not rely on memory. Plain fetch to https://www.googleapis.com only; no SDK or new package
- [x] The token is never stored, cached, logged or echoed; responses are not cached in KV (the point is freshness) and carry Cache-Control: no-store; a test proves the token appears in no log line, KV key or value, or response
- [x] Errors mapped and declared in the spec: missing/malformed header 400; Google 401 -> 401 google_auth (the app must refresh its token); 403/404 per calendar -> that calendar's status; Google 429/5xx -> 502 or per-calendar fetch_failed; our own rate limit 429 as on other routes (new limiter group or reuse of calendar's; keep RATE_LIMITS equal to wrangler.jsonc). Request bodies and outbound time capped like other routes
- [x] Tests with mocked Google responses (timed, all-day, multi-day, recurring instances, cancelled, paging via nextPageToken, error cases); npm test and tsc pass; npm run openapi regenerates openapi/openapi.json and the Swift client regenerates; the iOS app still builds and its suite passes on one runtime
