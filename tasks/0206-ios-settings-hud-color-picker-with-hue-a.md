## Goal

The user (2026-11-23): replace the hue slider with a color picker: a block where the existing colors (the current per-hue accent) are the floor along the bottom and fade all the way up to white at the top; the user can pick any point in the block. Horizontal position is hue, vertical is lightness. Add Settings.hudLightness: Double? (nil or 0 = the existing color for that hue, 1 = white), keep Settings.hudHue. HUDAccent gets a pure function of (hue, lightness) that returns exactly today's color at lightness 0 and white at 1, rising evenly in between. The user's request replaces the old ceiling (3:1 from the white date tile): the two floors stay and must hold everywhere in the block (4.5:1 on the plate, 4.5:1 for dark text on a fill). Default is still the orange-red (hue nil, lightness nil); the Default link resets both. The preview and note stay as they are.

## Acceptance criteria

- [ ] Pure color function tested over a grid of every whole degree by at least 21 lightness steps: both floors hold; lightness 0 equals the existing color for every degree; lightness 1 is white; luminance never falls as lightness rises
- [ ] Old-schema store test for Settings.hudLightness; a picked color survives relaunch; Default clears hue and lightness (model tests)
- [ ] The block is drawn from the color function (not a stock gradient that could differ from what is picked), with a marker at the current choice; a drag or tap anywhere in it sets both values; VoiceOver can adjust hue and lightness separately with spoken values
- [ ] Screenshots on the iPhone 17: Settings with the picker at the default, a pale pick and white; Today at a pale pick and at white; xcodebuild test passes on both runtimes

## What's been tried

- By-hand scroll check: a slow (1 s) axe swipe starting 14 pt above the block's top edge, at (250,545) on iPhone 17, did not scroll and set the colour (233 / 100 %): the block's pan and tap take touches that land just outside it (SwiftUI's hit testing gives a touch some area). The first time this was taken as 'slow swipes do not scroll', which it was not (the stored pick happened to equal what the swipe would write). Fix: the pan refuses to begin when its touch-down point (location minus translation, in the block's space) is outside the block, and a tap outside the block writes nothing.

- 2026-11-24T04:54:20Z [implementer-1] Mixing chosen (HUDAccent.rgb(hue:lightness:) / mix(_:toWhite:)): lightness 0 or nil returns rgb(hue:) unchanged (hue nil mixes from defaultRGB exactly), >= 1 returns white, non-finite is 0. In between: each component goes toward white in linear light (c -> c + s(1-c)), then 8-bit rounding; in linear light the line keeps the chromaticity, so the hue does not drift, and luminance is L0 + s(1-L0). s is set so CIE L* rises evenly from the floor's L* (55.34 for the orange-red) to 100: the stored lightness, the block's y-axis, the VoiceOver percent and -debugLightness all mean 'fraction of the L* distance to white'. Why L* and not a straight luminance share: by luminance the block's upper half would already look almost white (lightness 0.5 -> L 0.616, L* 83); by L* 0.5 looks halfway (L 0.527). Monotone: s rises with lightness, each linear component with s, sRGB encoding and rounding never go down, so luminance never falls; the mix only adds light, so both floors hold. Hand numbers (Python): orange-red at 0.25/0.4/0.5/0.75 -> (238,132,118)/(241,158,150)/(243,175,169)/(248,216,213).
