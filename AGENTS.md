# AGENTS.md

Read at the start of every session. `BUILD.md` says what is being built; `PROJECT-STATUS.md` says where the last session left off.

## RULES

Allowed without asking:

- Read and edit code in this project, run local dev servers, tests, type checks, and local D1 migrations.
- Generate the Xcode project (`xcodegen generate`), build and test the iOS app with `xcodebuild`, and run it in the Simulator (`xcrun simctl`).
- Regenerate the OpenAPI spec and the Swift client generated from it.
- Create and manage tasks with `./tasks/task`. This board is the only tracker; do not use GitHub issues, projects, or Actions.
- Use the `XcodeBuildMCP` tools to build, test, and drive the app in the Simulator.
- Commit locally.

Ask the user first:

- Deploying (`wrangler deploy`, `wrangler versions`), running anything against remote or production data (`wrangler d1 ... --remote`), creating or deleting cloud resources (`wrangler d1 create`, KV, R2, and the like), or setting secrets.
- Anything involving Apple signing or distribution: changing the bundle ID, team, entitlements, or capabilities; creating certificates or provisioning profiles; uploading to TestFlight or App Store Connect (fastlane, `xcrun altool`, Transporter); installing on a physical device.
- Adding a dependency or service that is not in STACK (npm package or Swift package).
- Deleting files you did not create this session.

Never:

- `git push`, force operations, or rewriting history.
- Read or write `.env*` (except `.env.example`, which you may read and write; placeholder values only), `.dev.vars*`, `*.toml`, or anything under `.wrangler/`, or print secrets. This holds for shell commands too: do not `cat`, `source`, or otherwise name those files in Bash. Wrangler config lives in `api/wrangler.jsonc`, which you may edit.
- Read, write, or print Apple signing material: `*.p8` (including `AuthKey_*.p8`), `*.p12`, `*.cer`, `*.mobileprovision`, or keychain contents.
- Hand-edit `*.xcodeproj` / `project.pbxproj`. Change `ios/project.yml` and run `xcodegen generate`.
- Hand-edit generated code (the generated Swift API client, `openapi/openapi.json`). Change the source and regenerate.
- Change `PROJECT-STATUS.md` or a task file through the shell (`sed -i`, `>`, `rm`, and so on).
- Edit `tasks/NNNN-*.md` directly. Use the CLI.
- Rewrite or delete existing entries in `PROJECT-STATUS.md` or a task log. Both are append-only.

Always:

- Work only on a task you have claimed. If the work has no task, create one.
- Put the task ID in each commit message: `[#42] ...` (or `[no-task]` when no task applies).
- Verify work by running it before moving a task to `review`: `npm test` and type checks in `api/`; `xcodebuild ... test` (or the XcodeBuildMCP test tool) for iOS changes.
- For a change to what the user sees, run the app in the Simulator and take a screenshot with XcodeBuildMCP before moving the task to `review`.
- When an API route changes, regenerate the spec and the Swift client in the same task, and make sure the iOS app still builds.
- Scope every D1 query on user data by the authenticated user ID from the session, never by client input.
- Save agreed plans in `plans/` and lasting decisions in `memory/decisions/`.
- End the session with the `session-wrap-up` skill.

Hooks and the permissions in `.claude/settings.json` enforce several of these. If a hook blocks you, follow its message; do not work around it.

## STACK

Native iOS app talking to a JSON API on Cloudflare. Business logic (weather, calendar links, followed sites, AI search) lives in the API so a later Android client can reuse it; the iOS app is UI plus local storage. The app works signed out: data stays in SwiftData until the user signs in, and the v1 routes need no account.

**API (`api/`)**

| layer | choice |
|---|---|
| Runtime | Cloudflare Workers (TypeScript, strict), configured in `api/wrangler.jsonc` |
| Routing | Hono with `@hono/zod-openapi`; Zod validates every request |
| Database | Cloudflare D1 (SQLite) through Drizzle ORM; schema in `api/src/db/schema.ts`, migrations generated by `drizzle-kit` into `api/migrations/` and applied with `wrangler d1 migrations apply` |
| Auth | Better Auth on D1 (Drizzle adapter), mounted at `/api/auth/*`; `bearer` plugin for mobile tokens; Apple provider with `appBundleIdentifier` set, using the native ID-token sign-in. Create the `auth` instance per request from the environment bindings |
| Cache / jobs | Workers KV for weather, calendar and feed fetches. The Cron Trigger morning refresh comes with sync (task 13); in v1 the feed refreshes when the app opens |
| Rate limits | Workers Rate Limiting binding (`ratelimits` in `api/wrangler.jsonc`), per client IP on the open `/v1` routes |
| Tests | Vitest with `@cloudflare/vitest-plugin` |
| Package manager | npm |
| Weather and sun/moon, temp, conditions | Open-Meteo, including its geocoder (5-digit US zip → place and timezone) |
| Calendars | `.ics` links pasted by the user (Google secret iCal address, Apple and Outlook published links), fetched by the Worker and parsed with `ical.js` |
| Followed sites | The page's advertised RSS/Atom feed parsed with `fast-xml-parser`; otherwise article links read from the HTML with the built-in `HTMLRewriter` |
| AI search | One adapter per provider (Anthropic, OpenAI, Google Gemini, Perplexity) called with plain `fetch`, no SDKs. The user's key arrives in a request header and is never stored or logged |
| Outbound fetches | User-supplied URLs go through one helper: https only, no private or local hosts, size and time caps. KV keys for calendar links are hashes, since a link is a credential |

**Contract (`openapi/`)**

| layer | choice |
|---|---|
| Spec | `openapi/openapi.json`, generated from the Hono routes (source of truth for clients) |
| Swift client | `swift-openapi-generator` + `swift-openapi-urlsession`, generated from the spec |

**iOS app (`ios/`)**

| layer | choice |
|---|---|
| Language / UI | Swift 6, SwiftUI, Observation (`@Observable`), iOS 18+ |
| Project | XcodeGen (`ios/project.yml`) |
| Local store | SwiftData; the UI reads local data first, then syncs from the API |
| Auth | AuthenticationServices (Sign in with Apple) → Apple ID token sent to Better Auth → session token stored in the Keychain |
| Identity | Bundle ID and team ID come from `app-identity.xcconfig` at the repository root, loaded by `ios/project.yml`. `api/wrangler.jsonc` repeats the bundle ID; a check in `npm test` fails if they differ |
| Secrets on device | Keychain for the session token and the user's LLM API key |
| Fonts | Bundled open-licence fonts: Jost (caps text) and a condensed bold face for the day name |
| Platform features | None in v1. The app asks for no location or calendar permission. Later ideas, not v1: Speech (voice input), App Intents (Siri / Shortcuts), WidgetKit, BackgroundTasks + UserNotifications |
| Tests | Swift Testing, run with `xcodebuild test` |
| Packages | Swift Package Manager |

App Store requirements to keep in mind: in-app account deletion (`DELETE /v1/account`), and Apple sends the user's email only on the first Sign in with Apple, so store it then.

The app is not scaffolded yet. The `scaffold-app` skill creates `api/`, `openapi/`, and `ios/` as described here; run it under a claimed task.

## TOOLS

MCP servers, defined in `.mcp.json`:

| server | where | use for |
|---|---|---|
| `XcodeBuildMCP` | local, `npx -y xcodebuildmcp@latest mcp` | building and testing the iOS app, booting and controlling the Simulator, screenshots, UI automation, LLDB. Prefer it over raw `xcodebuild` / `xcrun simctl`. The physical-device tools are switched off |
| `sosumi` | hosted, `https://sosumi.ai/mcp` | Apple developer documentation, Human Interface Guidelines, and WWDC transcripts |
| `cloudflare-docs` | hosted, `https://docs.mcp.cloudflare.com/mcp` | Workers, D1, KV, Cron Triggers, and Wrangler documentation |
| `cloudflare-api` | hosted, `https://mcp.cloudflare.com/mcp` | the user's Cloudflare account (Workers, D1). Signs in with OAuth. Read freely; ask before changing anything |
| `better-auth` | hosted, `https://mcp.better-auth.com/mcp` | Better Auth documentation |

Check these before writing framework code; APIs in this stack change often. For Apple frameworks, look the API up in `sosumi` instead of relying on memory, since SwiftUI and the iOS SDKs change every year. This Mac has Xcode 27.2 (iOS 27.2 SDK, Swift 6.4) with the iOS 18.3 and iOS 27.2 Simulator runtimes. The deployment target stays iOS 18, so guard any API newer than iOS 18 with `if #available`, and test on both runtimes.

CLIs:

| command | use for |
|---|---|
| `./tasks/task` | the task board (`./tasks/task help`) |
| `npx wrangler` | local dev, D1, types, deploys (run from `api/`) |
| `npx drizzle-kit` | generate D1 migrations from the Drizzle schema |
| `npx auth@latest` | Better Auth schema generation (Drizzle output) |
| `npm run openapi` | write `openapi/openapi.json` from the API routes |
| `xcodegen` | generate the Xcode project from `ios/project.yml` |
| `npx -y npm@11 install` | adding or upgrading a package in `api/`: the installed npm 10.9.2 crashes when it has to change the dependency tree. `npm ci` and `npm test` work as normal |
| `xcodebuild` | build and test the iOS app, e.g. `xcodebuild -project ios/Seasign.xcodeproj -scheme Seasign -destination 'platform=iOS Simulator,name=iPhone 16,OS=18.3.1' -skipPackagePluginValidation test` (use `name=iPhone 17` for iOS 27.2; without `OS=` xcodebuild looks only in the newest runtime). The flag is required, or the OpenAPI build plugin is refused |
| `xcrun simctl` | boot, install to, and control the Simulator |
| `git` | local version control (no remote; never push) |

## ROLES

**Lead session** (the session the user talks to). Owns the plan and the board. It reads this file and the status entry, turns BUILD.md into tasks, claims and delegates them, reviews results, decides what is done, and writes the status entry at the end. It keeps its own context for coordination and hands implementation to subagents when a task is self-contained.

**Advisor model.** The lead is paired with a stronger model through the `advisorModel` setting (`/advisor` shows or changes it). The advisor sees the whole conversation and gives guidance; it does not act. Consult it before committing to an approach, when the same error comes back, and before declaring a task or the session done. Subagents inherit the advisor.

**Subagents**, defined in `.claude/agents/`:

| agent | job | rules |
|---|---|---|
| `implementer` | builds one task | given a task ID the lead claimed for it; logs notes; commits with the ID; moves the task to `review` |
| `reviewer` | checks a task in `review` against its criteria | does not change code or task state; reports pass or changes needed |

Managing subagents: one task per subagent, and the task file is the brief. Run tasks in parallel only when they touch different files. API and iOS tasks can usually run in parallel; anything that changes the OpenAPI spec cannot run alongside iOS work that depends on it. Nothing is `done` until a reviewer, or the lead, has checked it against the acceptance criteria. See the `task-workflow` skill.
