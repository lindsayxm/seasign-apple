# Architecture

Kept current by the lead session. The STACK section of `AGENTS.md` lists the chosen libraries; this file says how the parts fit together.

## Shape

```
iPhone app (ios/)  ──HTTPS, JSON──▶  API on Cloudflare Workers (api/)  ──▶  D1 (users, lists, follows)
   SwiftUI + SwiftData                  Hono + Zod + Better Auth        ──▶  KV (fetched news)
        ▲                                        │                      ◀──  Cron Trigger (morning refresh)
        └──── generated Swift client ◀── openapi/openapi.json ◀─────────┘
```

- **Business logic lives in the API** (weather and sun/moon, reading calendar links, fetching followed sites, AI search) so a later Android client can reuse it. The iOS app is UI plus local storage; it uses no location or calendar permission.
- **Signed out by default.** The v1 routes need no account: the app sends what the Worker needs with each request (zip, calendar links, site list, the user's LLM key) and keeps the user's data in SwiftData. Sign in with Apple and D1 sync come last (tasks 13 and 14).
- **User-supplied URLs** go through one safe-fetch helper in the Worker (https only, no private hosts, size and time caps). LLM keys and calendar links are never logged or stored; KV cache keys for calendars are hashes.
- **The OpenAPI spec is the contract.** It is generated from the Hono routes; the Swift client is generated from the spec. Neither is edited by hand.
- **Local first on the phone.** The UI reads SwiftData, then syncs from the API.
- **Auth.** Sign in with Apple on the device → Apple ID token → Better Auth → bearer session token in the Keychain. Every D1 query on user data is scoped by the session's user ID.

## How the pieces are wired

- **Spec to Swift.** `ios/project.yml` adds `openapi/openapi.json` and the generator config to the app target and runs the `OpenAPIGenerator` build plugin, so the Swift client is rebuilt from the spec on every build and never committed. After changing a route: `npm run openapi` in `api/`, then build the app. Both files sit in the Compile Sources phase so they are not shipped in the app; Xcode prints one harmless "no rule to process file" warning for each.
- **Command-line builds** need `-skipPackagePluginValidation` (XcodeBuildMCP: `extraArgs`), or the build plugin is refused. Use simulator IDs or exact names: iPhone 16 exists on iOS 18.3, iPhone 17 on iOS 27.2.
- **Simulators.** Build separately for each runtime: a Debug build made for the iOS 27.2 simulator does not launch on the 18.3 simulator, so build (or test) with the iPhone 16 selected before running there, and again with the iPhone 17. The UI automation tools can leave a simulator on the hardware keyboard, after which no on-screen keyboard appears; Simulator › I/O › Keyboard › Toggle Software Keyboard brings it back. XcodeBuildMCP keeps a test-products bundle of about 450 MB per test run under `~/Library/Developer/XcodeBuildMCP/workspaces/.../test-products`; clear old ones when disk is short.
- **Info.plist and fonts.** The app target has `info:` in `ios/project.yml`; XcodeGen writes `ios/Seasign/Info.plist` from it and Xcode merges the `INFOPLIST_KEY_*` build settings in at build time. The bundled fonts are listed there under `UIAppFonts` by file name; code refers to them by PostScript name (`FontName` in `Design/Typography.swift`), and `DesignTests` fails if a name does not load. `TARGETED_DEVICE_FAMILY: "1"` has to be on each target, because XcodeGen's iOS target preset sets `1,2` and beats a project-level value.
- **Caps.** Text is shown in capitals by `Text(caps:)`, which capitalises the string and keeps the original as the accessibility label; `.caps()` / `.capsRelative()` set only font and letter spacing. Do not use `textCase(.uppercase)`: it also capitalises accessibility labels, explicit ones included.
- **Local stores.** One `ModelContainer`, two SQLite files in Application Support (`LocalStore`): `default.store` holds what the user entered (`Settings`, `ListItem`, `CalendarLink`, `Site`, `SavedItem`; `SeasignSchema.userModels`) and `SkyCache.store` holds copies of API responses (`CachedSky`, `CachedEvents`, `FeedItem`, `CachedFeedState`; `cacheModels`). If the container will not open, it is tried again with the cache in memory: when that works the user store is healthy, so only the cache file (with its `-wal` and `-shm`) is deleted and recreated, and if no cache file can be made the in-memory one serves for that launch. Every open uses the full schema, the configurations only route models to files (each file carries every model's table); opening `default.store` with fewer models would make Core Data migrate it. If the user store will not open, nothing is deleted and `StoreErrorView` offers Try again. Put a new model in `cacheModels` only if all of it can be fetched again. No migration plan is used; SwiftData's automatic lightweight migration covers added optional fields and added models (task 6 added `CalendarLink` and `CachedEvents`, task 8 `Site`, `FeedItem` and `CachedFeedState`, task 9 `SavedItem`, task 12 `SearchCount` and optional fields on `Settings`, `SavedItem` and `FeedItem`; `LocalStoreTests` opens stores written with the earlier schema and checks nothing is lost and the cache file is kept. When a task changes an existing model, the test declares the old version of that class again under the same name in an enum (`Task11Schema`), which SwiftData maps to the same entity; new fields on existing models are optional with nil meaning the old behaviour, and a column's type or optionality is not changed, which is why `FeedItem.siteID` stays non-optional and AI rows store `FeedItem.noSite`).
- **Scene rules** (all in `Scene/SkyMath.swift` and `SceneState.swift`, unit-tested). The sun and moon are placed from the rise and set instants on either side of now, not by pairing a date's rise with its set. The moon estimates a missing end with a 12.4 h arc; the sun never assumes a day length: with a sunrise or sunset missing, `isDay` decides unless a known sun event has happened since the reading. Discs take 15 minutes to rise out of and sink into the water (`SkyBodyState.placement`); the moon is drawn only when no part of the sun shows. A cached sky that covers today's date keeps placing sun and moon, but its temperature and weather are shown only within 3 hours of the fetch (`SkySnapshot.currentIsFresh`); a cache without today falls back to the neutral 06:00–18:00 scene. Redraw rate follows `SceneMotion`: 30 fps for rain, snow or wind, 10 fps for clouds, one redraw every 3 s on a clear night, one still frame otherwise or with Reduce Motion.
- **Debug launch arguments** (Debug builds only; read from `UserDefaults`, so they are passed as `-key value`, and the first three can also be set in Settings › Debug scene): `-debugTime sunrise|midday|sunset|night|moonrise|moonset`, optionally with an offset in minutes (`sunrise-5`, `sunset+7.5`, `moonset+8`); `-debugMoon 0…1` (phase; implies night); `-debugWeather clear|cloudy|windy|rain|snow`; `-debugStoreFailure YES` shows `StoreErrorView` without touching a store; `-debugEvents YES` shows two sample calendar links and three sample events from a store in memory (`EventsModel.sample`), fetching nothing and leaving the user's store alone; `-debugFeed YES` shows three sample sites (one failing with `timeout`), five headlines and three older items for History from a store in memory (`FeedModel.sample`), likewise; `-debugSaved YES` shows three saved articles (one with notes, one whose feed item is not cached; `SavedModel.sample`). `-debugAI YES` (implies the feed sample) shows AI search configured and on, with the fake key `test-key-not-real-0000` in an `InMemoryKeyStore`, three interests, 2 of 3 searches used, and three AI-found items (two on Today, one in History; with `-debugSaved YES` also one AI-found saved article); it sends nothing (`AISearchModel.sample` is frozen) and touches neither the user store nor the real Keychain. If the feed sample cannot be built, `-debugAI` still never uses the real Keychain: it gets `AISearchModel.debugFallback` (the fake key in an `InMemoryKeyStore`, frozen), in the in-memory store when one could be made (`DebugAIFallbackTests`). With any of the last three, the samples share one in-memory store (`SeasignApp.debugSamples`), so saving a sample headline never writes to the user store. None of these strings is in a Release build (checked with `grep -a` on the built app in task 12). Example: `xcrun simctl launch --terminate-running-process <udid> com.example.seasign -debugTime sunset+5 -debugWeather clear`.
- **Calendar links on the phone.** A link is a credential. It is stored only in `CalendarLink.url` (user store) and sent only in the body of `POST /v1/calendar/events`. Nothing else may hold it: `SeasignAPI.calendarEvents` drops the generated client's error (its description includes the request) and throws a payload-free `CalendarFailure`; messages come from fixed text (`LinkProblem.message`, `EventsModel.AddProblem.message`); Settings shows the name and `LinkMask.host(of:)` (the last two labels of the host, three for `co.uk`-style suffixes); the cache (`CachedEvents`, a JSON `EventsSnapshot`) ties events and per-link status to `CalendarLink.id`. Do not interpolate a `CalendarLink` or its `url` into a string, a log or an accessibility label. The app imports no EventKit and has no calendar usage string (`NoCalendarPermissionTests`).
- **Events on Today.** `EventsModel` (in the environment next to `TodayModel`) loads the links and the cached snapshot at launch, and `refresh()` runs at launch, every minute while Today is open, on return to the foreground and when the events' time zone changes; a snapshot younger than 10 minutes that covers every link is not fetched again. The time zone is `EventZone.resolve`: the zip's zone when a zip is set and its sky is known, otherwise the phone's. It is sent as `timezone` and used for formatting. A snapshot made for another zone is dropped and refetched, because all-day events were placed in the zone they were asked for. Adding a link asks the API for that one link (the check and its events in one request); a failed link is not saved. A whole-request failure keeps what is on screen. Per link: a failure shows only in Settings; events of a link that failed with `fetch_failed` or `timeout` are carried over from the previous snapshot until they end; any other failure drops them. Removing a link drops its events at once.
- **Which events and how they read** (`EventPicker`, `EventLabel`; pure, unit-tested). Not ended by the API's rule (an event without a length is over once it has started), soonest first, all-day before timed at the same instant, three at most; the Today clock tick drops events as they end. Time is `10:15AM` (12-hour, built by hand, so the device's 24-hour setting does not change it); all-day events read `ALL DAY` and belong to their `date` string whatever the zone; an event starting on a later day gets the day first (`TUE 9:00AM`, `TUE ALL DAY`), one that began before today and is still running does not; an empty title reads `No title`. `EventsColumn` shows as many of the three as fit above the header rule; the "set your zip" prompt stands alone when there are no events and goes under the events only if it fits.
- **Followed sites on the phone (task 8).** `Site` (user store) keeps the address in the API's normal form (resolve's `url`), mode, feed address, the site's title (cleaned) and the user's own category; `FeedItem` (cache store) keeps one row per article link with a copy of the category taken at fetch time, `siteID` and `firstFetchedAt`; `CachedFeedState` is one JSON row with each site's last problem and when the last full refresh succeeded (no addresses). Adding: the typed text gets `https://` when it has no `://` and `http://` becomes `https://` (`SiteAddress.normalize`); `url` plus `feedUrl` may take 560 UTF-8 bytes, so 50 sites always fit the API's 64 KB body (a test sends 50 at the limit made of escaped characters); then `POST /v1/sites/resolve`: a failure shows `SiteProblem.message` and saves nothing, links mode with `linkCount` 0 is refused as having no articles, an answer without `url`/`mode` (or feed mode without `feedUrl`) counts as unavailable, the normal form is checked again for duplicates, and after saving only the new site is fetched. A category matching one in use ignoring case takes that spelling; Settings offers the ones in use as chips. At most 50 sites. Refresh (`FeedModel.refresh`): at launch and on return to the foreground, not on Today's one-minute loop, plus "Refresh headlines now" in Settings; skipped when the last full refresh is under 15 minutes old and every site has a status; one request for all sites; overlapping refreshes are dropped. Answers are merged by link (`FeedStore.upsert`: new links inserted, known ones updated, `firstFetchedAt` kept, nothing removed because it is missing from an answer, so task 9's history keeps it); items are mapped to sites through the ids captured before the request, so a site removed meanwhile gets nothing. A failing site keeps its items and shows its problem under it in Settings; a whole-request failure changes nothing. Items dated more than 7 days ago are pruned on load and on every refresh; removing a site deletes its items and status at once. `FeedStore.item(link:)` finds an item again by its link.
- **Headlines on Today.** `HeadlinePicker.sinceYesterday`: items dated since midnight at the start of yesterday (calendar days, so daylight-saving days are right) in `EventZone.resolve`'s zone (the zip's when known, else the phone's), newest first, ties by link. `HeadlinesColumn` shows as many as fit whole above `>>`, at most 5 (`HeadlineFit.maxCount`): each headline's height is its line count from `CapsWrapper.wrap` (two lines at most, the second ending in "…") times the 14.5 pt pitch, and `HeadlineFit.count` takes the longest run from the newest that fits with the 28.5 pt spacing. No `ViewThatFits` and no scroll view. With no site followed one quiet line ("Follow sites in Settings to see headlines here") opens Settings; with sites but nothing since yesterday the water is empty.
- **Saved and History (task 9).** `SavedItem` (user store) is a full copy taken at save time: link, title, source, published, dateSource, excerpt, category, notes, savedAt, updatedAt, and a sync `id`. It never refers to a `FeedItem`, so it outlives the 7-day prune and the deletion of an unfollowed site's items (`SavedModelTests.savedSurvivesSiteRemovalAndPruning`). One row per link, enforced by `SavedModel.save` looking the link up first; `@Attribute(.unique)` is not used because a second insert would replace the row, notes and all. Saving again does nothing. Title, source and excerpt are cleaned again with `SiteText.clean` when saved; links that `ArticleLink.url` refuses are not saved. Views and dialogs hold value copies (`SavedEntry`, `ReadingItem`, `RemovalConfirmation`), never rows. The reading view takes a `ReadingItem`, so it opens a saved article whose feed item is gone; its save mark toggles, and un-saving an article with notes asks first. REMOVE in Saved removes at once unless the article has notes (a draft not yet written counts), then asks. **Notes**: the user's writing, kept as typed (no cleaning, line breaks kept), capped at 2,000 characters (`SavedModel.notesLimit`) in the binding so the field shows what is stored. What is typed lives in `SavedModel.drafts` (not in a view, so a lazy row scrolled away or a closed screen loses nothing) and is written 0.8 s after typing stops, when a notes field loses focus, when Saved appears or disappears, when Close is tapped, and when the scene leaves `.active` (both in Saved and in `TodayView`'s scene-phase handler). Each write assigns and saves at once, so another model's `rollback()` on the shared main context cannot undo it. A failed write rolls the context back but keeps the draft (on screen and in memory), sets `problem = .notesNotSaved` (shown with Try again) and is retried on the next flush; Close then asks before leaving. Removing an article drops its draft and pending write. **History** reads `FeedModel.entries` (cache store) and filters at query time too (`HistoryList.visible`: not older than 7 days by `FeedEntry.isExpired`, newest first), because the cache is pruned only on load and refresh. **Search** (`ArticleQuery`) is plain in-memory text matching on title and source: every typed word must appear in one of them, ignoring case, accents and width, curly quotes read as straight; nothing typed becomes a predicate or pattern. Notes are not searched, so a row never vanishes while its notes are typed. The category menu lists the distinct categories present in that list (`CategoryName.distinct`; History from the items' copied category, Saved from the saved copy) and falls back to All when the chosen one disappears. Dates on rows are `ReadingDate.day` (`Nov 10, 2026`) in the zip's zone. Accessibility labels for save and remove include the title, built as `String`s (`SaveMark.label`).
- **Site text is untrusted.** Titles, sources, excerpts and site titles go through `SiteText.clean` before they are stored (white space collapsed, control and invisible format characters such as bidirectional overrides dropped, emoji joiners kept, capped at 300/120/600 characters on a character boundary) and are shown only through `Text(verbatim:)` or `Text(caps:)`, which is verbatim too (as is `WrappedCaps`); labels that include one are built as `String`s, never interpolated `LocalizedStringKey`s, so no Markdown or link is ever read from a site. Items whose link is not https with a host (and no user or password) are dropped (`ArticleLink.url`). The reading view opens the link with SwiftUI's `openURL`, so it leaves the app for the user's default browser (their subscriptions and content blockers apply, and the page never runs inside the app); `SFSafariViewController` was not used because it shares no cookies with Safari, so paywalled sites would not know the user. No web view is used anywhere.
- **AI search on the phone (task 12).** `AISearchModel` (in the environment next to `FeedModel`) owns the settings behind the pill, the key, the daily count and the searches; `FeedModel` only blends and shows. Rules:
  - **The key's status** is `KeyStatus`: `.saved`, `.missing` (the Keychain answered and holds none) or `.unknown` (the read failed, e.g. `errSecInteractionNotAllowed` before the first unlock after a restart). `hasKey` is `.saved` only. `.unknown` never sends (`SearchGate` gives `.notReady(.keyUnreadable)`), never moves the pill and never asks for the key (AI-found items are hidden while it lasts, since AI search is not active): the precondition reads "AI search waits until your saved key can be read", Settings shows "Key can't be read now" with Try again and Replace instead of the key field, and the `keyUnreadable` problem says to unlock the phone. The Keychain is read again at the start of every search attempt (`run`, before the gate), when the scene becomes active (`TodayView`, before `refreshIfDue`) and when the Settings AI section appears; a read that finds the key clears a `keyUnreadable` problem (also one stored by an earlier launch), one that finds none applies the launch rule (back to Use My List).
  - **The key** lives only in the Keychain: one generic password, service `seasign.llm-api-key`, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, not synchronisable; no entitlement needed (a real round trip runs in `KeychainKeyStoreTests` under a test service). Access goes through `APIKeyStore`, so tests and the DEBUG sample use `InMemoryKeyStore`. The key is an `APIKey` (prints, debug-prints and reflects as `<redacted>`, not Codable), read from the Keychain at send time and passed straight to `SeasignAPI.discover`; no model property holds it. Accepted shape: 16 to 512 bytes of 0x21 to 0x7E after trimming, checked at save so a malformed key never costs a 400. Settings shows "Key saved" with no characters of the key (a tail would be key material on screen, in accessibility and in screenshots), with Replace and Remove; the entry is a `SecureField` with autocorrection and capitalisation off, emptied as soon as Save is tapped. One key; changing provider keeps it and shows a reminder that it must be that provider's.
  - **The header.** The generated client writes header parameters as URI components (`setHeaderFieldAsURI`, percent-encoding everything but unreserved characters), so a key holding `/`, `+`, `=` or `%` would arrive as a different key. `RawKeyHeader` (a `ClientMiddleware`) percent-decodes `x-llm-key` back to the exact bytes before the transport; `DiscoverAPITests` checks keys of every printable character arrive byte-identical. `discover` maps by status code alone and throws the payload-free `DiscoverFailure`; the generated client's error, which describes the request with its headers, is dropped.
  - **No redirects, https only (task 21).** URLSession follows redirects by default and sends custom headers again to the new address (tested: 301, 302, 303, 307 and 308 all delivered `X-LLM-Key` to the target). Every `SeasignAPI` call goes through `SeasignAPI.session`: one shared ephemeral session (no cookie store, cache or credential store; shared because a session with a delegate lives until invalidated) whose delegate `RefuseRedirects` passes nil to `willPerformHTTPRedirection`, so the task completes with the 3xx answer, which every wrapper maps to its `unavailable`. The transport is swift-openapi-urlsession in `.buffered` mode: its streaming mode puts a per-task delegate on each task (it did not take over redirects in a test on both runtimes, but buffered leaves the session delegate as the only one). `RedirectTests` prove it with two loopback servers (`LocalHTTPServer`; `acceptLocalOnly` must stay off, it resets every connection in the Simulator). `discover` also refuses, before any request, a server that is not https when `keyNeedsHTTPS` is on (the default outside DEBUG, `SeasignAPI.keyNeedsHTTPSByDefault`; injected in tests), failing as `unavailable`.
  - **Settings** (user store, all optional on `Settings`): `aiModeRaw` (nil is Use My List), `aiProviderRaw`, `aiInterestsText` (as typed; `InterestList.parse` splits on commas, cleans with `SiteText.clean`, drops empties and case-insensitive repeats, cuts each to fit the API and keeps 20, with a message when it cut or dropped). - **ical.js only parses; nothing that repeats ever reaches it.** One call to ical.js's recurrence iterator cannot be interrupted, and rules exist that make it search for a date that never comes (`FREQ=MONTHLY;INTERVAL=48;BYDAY=5MO` from a February that is never in a leap year ran 45 s and more). It runs that iterator for an event's RRULE and, the first time a zone is used, for a VTIMEZONE's rules. A filter in front of it was got around three times (a rule shape the whitelist missed, twice; then a folded property name the text-level rename missed), so there is no filter any more. In `api/src/lib/calendar.ts`, ical.js (2.x) does two things: `ICAL.parse` turns the text into data, and its value classes decode a time, a duration or the parts of a rule. Then: (1) `cleanEvent` rebuilds every VEVENT from nine named properties with the value types expected of them, plus the event's rules as plain text under a name ical.js has no meaning for; alarms and anything nested are left behind. However a rule was written (case, fold, group, parameters, `VALUE=RECUR` on another property), it cannot arrive as a rule. (2) No VTIMEZONE is ever given to an ical.js object. (3) `readRule` and `expandRule` expand rules: the walk goes through the rule's periods (days, weeks, months or years) by index and works out each period's days with plain arithmetic. It ends for any rule, because each period starts later than the one before and the walk stops at the first period past the window. Without COUNT it starts at the window; with COUNT it counts from DTSTART. `api/test/calendar-smuggling.test.ts` replaces ical.js's iterator, zone expansion and offset methods with functions that throw and checks after every test that none was reached. Do not add a call to `ICAL.Event`, `RecurExpansion`, `Recur#iterator`, `Timezone#utcOffset` or `Time#toUnixTime` on file data.
- **Rules supported.** Daily, weekly, monthly, yearly with INTERVAL, COUNT, UNTIL, WKST, BYDAY, BYMONTHDAY, BYMONTH, BYSETPOS, in any letter case. Skipped (the calendar is then `partial`): rules finer than a day, BYHOUR and finer, BYWEEKNO, BYYEARDAY, a yearly rule with BYDAY or BYMONTHDAY but no BYMONTH, EXRULE, and any malformed rule. Before `ICAL.parse`, lines are unfolded (CRLF, LF or CR followed by a space or tab) and `readableLines` reduces the file to what the reader uses, in one pass: the VCALENDARs and the VEVENTs and VTIMEZONEs directly inside them, with only the properties `cleanEvent` and `readZone` read, only their TZID, RANGE and date-typed VALUE parameters, and RRULE/EXRULE renamed to plain text (what it bounds is under Calendar memory limits). Each line handed on is rebuilt from its name, those parameters and its value, never passed through as written; a TZID or RANGE is handed on only in a form ical.js reads exactly as we do (`HANDED_PARAMETER`: in quotes with no quote or backslash inside, or bare with no quote, `;`, `:` or backslash; 300 characters at most), the last of each as ical.js would take it, and VALUE only as `DATE` or `DATE-TIME`. A TZID left out for its form makes the time floating, like a TZID nobody can interpret, and sets `partial` when the line is in an event (zones read no TZID parameter); a RANGE left out is not reported, since nothing reads it. Apart from those limits this is for robustness and speed, not safety: ical.js rejects a whole file for one value it cannot decode (a malformed rule, or any value marked `VALUE=RECUR` or `VALUE=PERIOD`) and takes 2 to 3 s over a line with 200,000 parameters. A line that is not a property at all is left out and sets `partial`. Where ical.js and RFC 5545 disagree we follow the RFC: DTSTART always counts as the first of COUNT; a monthly rule with INTERVAL and BYMONTH keeps to the interval's months; the last day of February stays in February; months without the day (the 31st, 29 February) are skipped. An UNTIL earlier than DTSTART leaves DTSTART alone. `RANGE=THISANDFUTURE` overrides change only their own instance. `EXDATE;VALUE=DATE` on a timed series removes that local day. A file may hold several VCALENDARs (20 are read). A VEVENT or VTIMEZONE nested in another component is not read and sets `partial`.
- **Calendar CPU limits.** A calendar file is untrusted input. (1) Every loop over a repeat rule or a zone's rules is ours and is charged to a work budget per file (`MAX_WORK_PER_FILE`); when it runs out, reading stops and the calendar is `partial`. (2) A VTIMEZONE may have 60 blocks, 12 rules and 400 listed dates, and a file 50 zones; a zone's changes are worked out a year at a time and only for times within three days of the kept window. (3) Every time zone lookup is charged to the budget too (10 units), a file may name 50 distinct TZIDs it does not define (`Intl` accepts any capitalisation and builds a formatter per spelling; later names are read as floating), and a series that began long ago is not looked up at all. (4) Each VEVENT is wrapped in an ical.js component of its own, with no parent, only while it is read: for each time with a TZID, ical.js searches the root calendar's children for a VTIMEZONE, which took 8 s for 30,000 events side by side (task 5 moved them into one component of their own; task 18 gave each its own wrapper, which also lets ical.js's decoded values go once the event is read). (5) An event listing more than 2,000 EXDATE and RDATE values is skipped. (6) At most 500 occurrences are kept per calendar. `Date.now()` does not advance during CPU work in a Worker, so a time budget would not work. Measured in Node on files of 1 to 3 MB (the fetch cap is 2 MB): of twelve hostile or very large files the slowest takes about 0.35 s (9,000 yearly rules over all twelve months with COUNT, from 1900).
- **Calendar memory limits (task 18).** CPU on the calendar path is charged to a budget as the work is done; memory cannot be, because `ICAL.parse` builds its whole tree at once, about 0.5 KB per line it is handed (a measured 560 B per EXDATE line in jCal, and another 500 B per value once decoded into an `ICAL.Time`, which ical.js then keeps on the component). So `readableLines` bounds what ical.js is handed, in one pass over the unfolded text that never splits it into a list of lines. It tracks components as ical.js does (by count; END closes whatever is open; a stray END with nothing open is ignored, as ical.js lets one at the end of a file pass) and hands on only VCALENDARs and the VEVENTs and VTIMEZONEs directly inside them. Alarms, unknown components and anything nested are counted to find their end but not kept, and a VEVENT or VTIMEZONE among them sets `partial`; the calendar's own properties are not kept (nothing reads them). In an event: the first of each of UID, SUMMARY, STATUS, DTSTART, DTEND, DURATION, RECURRENCE-ID (the one read); up to 8 RRULE/EXRULE lines and up to 2,000 EXDATE/RDATE values (counted as ical.js splits them: at each comma not right after a backslash, on the very value handed on), else the event is left out and the calendar is `partial`. In a zone: the first TZID, and per STANDARD/DAYLIGHT block the last DTSTART, TZOFFSETFROM and TZOFFSETTO (the ones `readZone` uses) plus its RRULEs and RDATEs; a zone that `readZone` would refuse for size (more than 60 blocks, 12 rules or 400 listed dates, counted raw, or EXRULE or a rule under another name) is not handed on, nor are zones after 100. File limits, over which the whole file is refused with `CalendarTooLargeError` (a `CalendarParseError`; the route answers `too_large`): `MAX_CALENDAR_BYTES` 2 MB of text (also passed to `safeFetch`, and checked in `parseCalendar` in characters, which are never more than the bytes), `MAX_EVENTS_PER_FILE` 12,000 VEVENTs, `MAX_LINES_PER_FILE` 60,000 lines handed on (BEGIN and END included), `MAX_LISTED_PER_FILE` 20,000 EXDATE and RDATE values. The file limits refuse rather than read a part, because file order is not date order and a part would quietly lose events that are coming up. After parsing, each event gets its own ical.js component with no parent, used while it is read and then let go, and `expand` counts EXDATE/RDATE from the jCal before decoding (then decodes them all before placing anything, so an undecodable value still skips the whole event). - **Followed sites.** The app stores `{ url, mode, feedUrl? }` per site and sends the list with each `/v1/feed` request; the API keeps nothing about a user. A site address is never logged or put in an error (log lines carry the index and a code), though it is not a credential. `POST /v1/sites/resolve` takes `{ url }`, fetches the page and answers 200 with `{ ok: true, title, url, mode, feedUrl?, linkCount? }` or `{ ok: false, error }`; `url` is the typed address in normal form, not the redirect target. An address that is itself a feed gives mode `feed` with that address and no `linkCount`. For a web page, `linkCount` is how many article links the page shows now (at most 200), so the app can warn when links mode would give nothing. The page's `<link rel="alternate">` feeds (RSS, Atom and RDF types; `text/xml` or `application/xml` only when the title or address says rss, atom or feed; never a `rel` that includes `stylesheet`) are resolved against the answering address and `<base>`, checked with the safe-URL rules, and ordered: not a comments feed, then most leading path segments shared with the page, then document order. Which are asked for: on a site's front page, or on a page with no article links, any of them; on any other page only feeds that share the page's first path segment, because a feed that shares nothing is most likely the whole site's and would bring in every section (the live check below is where this came from). At most two are fetched and the first that answers with a real feed wins; otherwise the mode is `links`. A feed on another host (a feed service) shares no path, so a section page whose only feed is hosted elsewhere is followed by its links. What a response is (`bodyKind`) goes by its first element before its Content-Type, because feeds are served as `text/html` and pages as `text/plain`; leading comments and processing instructions are stepped over, not searched, so `<!-- <rss> -->` in front of a page does not make it a feed.
- **`POST /v1/feed`.** Body `{ sites: [{ url, mode, feedUrl? }] }`, 1 to 50; a bad body or a body not sent as `application/json` is the fixed 400 `invalid_request`. The answer is `{ items, sites: [{ index, ok, error? }] }`; one failing site does not fail the rest, failures are not cached, and mode `feed` without `feedUrl` is that site's `invalid_url`. An item has `site` (index), `title`, `link`, `source`, `published` (UTC, second precision, never null), `dateSource` (`published` or `first_seen`) and `excerpt` (plain text, at most 300 characters, or null; always null in links mode). Every item has a time, so every item ages out: the 7-day window is applied when a site is fetched and again on every answer, and a cached site never returns an item that has aged out. A date up to a day ahead of the clock counts as now; later than that, the item is left out. An item with no readable date of its own, on a page or in a feed, gets a first-seen time (below). Order: newest first, then site index, then the site's own order. At most 30 items per site and 300 in all. A link is returned once, under the lowest site index that has it. Sites that are not in the cache are fetched 6 at a time, 6 seconds each, inside 20 seconds for the whole request (`performance.now()`, which like `Date.now()` moves with I/O in a Worker); a site not started by then is `timeout`. A site sent twice is read once. The cached value is `{ version: 2, source, items }`.
- **Feeds (`api/src/lib/feed-parse.ts`).** fast-xml-parser 5 with `preserveOrder` (so text, CDATA and nested XHTML keep their order), `processEntities: false` and `maxNestedTags: 64`. Before the parser sees the text, `checkShape` reads it once and refuses (`not_feed`) what the parser cannot hold in memory or should not see: more than 1 MB; a tag longer than 8,192 characters; more than 64 attributes on an element or processing instruction, counted with a copy of the parser's own attribute pattern (`attrsRegx`), which quotes do not stop, so `<x "a0='' a1='' …"/>` counts every pair inside the quotes as the parser does; more than 60,000 tags, comments, CDATA sections and processing instructions together; a run of text longer than 131,072 characters (`MAX_TEXT_RUN`; the parser builds text one character at a time and starts a new string only at a tag, a processing instruction or CDATA, so text either side of a comment or the DOCTYPE is one run, and so is text before the first tag or after the last; CDATA is taken in one piece and is not limited); a `<` that does not start one of those (`< `, `<<`); anything left unclosed; any declaration but one DOCTYPE (any letter case); and a DOCTYPE with an internal subset or any `<` inside it, which is where entities (billion laughs, external entities) are defined. It finds the end of each piece the way the parser does (quotes hide a `>` in an opening tag and a processing instruction, not in a closing tag; comments and CDATA are skipped whole), so a small tag there is a small tag here; re-read `readTagExp`, `tagExpWithClosingIndex`, `attrsRegx`, where `textData` is reset in `parseXml`, and `DocTypeReader.readDocType` when upgrading fast-xml-parser. The DOCTYPE that passes is cut out of the text before the parser sees it: it declares nothing we use, and the parser reads only an upper-case `<!DOCTYPE` as one (a lower-case `<!doctype rss>` became an element holding the whole feed, so the feed had no root). The parser also expands no entity, so a reference the document leaves undefined stays as written; our `decodeEntities` handles the XML five, numeric references and common HTML names, and cannot make text longer. Nesting past 64 or an element named `constructor` or `__proto__` makes the parser throw; every throw becomes `FeedParseError` without the parser's message, which quotes the input. A document is a feed by its root element (`rss` with a `channel`, `rdf:RDF`, `feed`), not by having parsed: HTML often parses. Dates are read by two anchored patterns on the first 64 characters (ISO 8601 / RFC 3339 and RFC 822), never by `Date.parse`, which accepts things like `"12"`. RFC 822 dates may leave out the space after the weekday's comma, may leave out the time (`Sat, 14 Nov 2026` is midnight UTC) and may end in a comment (`+0000 (UTC)`); the zone is an offset, GMT/UTC/UT with an offset (`GMT+1`, `UTC+01:00`, `GMT-0530`, read as that far east of UTC), or a name: about fifty zone names are known (where a name is ambiguous the common reading is taken: CST and EST North American, IST India) and an unknown name is read as UTC, since a date a few hours out is better than none; no zone means UTC. Any year the patterns can read counts, 0000 to 9999: a date before the 7-day window is old and the item is dropped (Hugo writes `Mon, 01 Jan 0001` for undated pages, which used to be read as no date and so got a first-seen time and showed as new), and one more than a day ahead is left out like any other future date (in links mode such a link gets a first-seen time, as before). Links are resolved against the answering address and `xml:base` (root, channel, item or entry, link), `http:` is read as `https:`, and each must pass `assertSafeUrl` or the item is dropped. RSS `description` and Atom `type="html"` are HTML written as text: escaped text is unescaped once, CDATA is taken as written, then `htmlToText` strips it.
- **Pages without a feed (`api/src/lib/page-links.ts`).** HTMLRewriter collects every `<a href>` with its text, whether it sits in `<nav>`/`<footer>`, and whether it is "preferred" (inside `<article>`, `<main>` or an h1-h3, or wrapping one). `articleLinks` keeps a link when it is outside nav and footer; resolves to a safe https URL on the page's host (same host name ignoring a leading `www.`; there is no public-suffix list, so other subdomains do not count); has an article-like address; and has headline-length text. The address rule (`isArticlePath`), in order: the page itself or a page above it is out unless its query names an article (`/index.php?p=77` from `/index.php?cat=2`; the parameters are `id`, `p`, `article`, `story`, `post`, `item` and their `...id` forms); a file that is not a page (`.pdf`, `.jpg`) is out; after the part of the path shared with the page, a segment naming something else (sign-in, search, about, `page/2`, `index.html`) puts it out, and a `tag`, `author` or `category` segment is allowed only with a date in the path (`/category/tech/2026/11/15/a-story`) or two more segments ending in a slug; then one of these must hold: an article query, more segments than the page, a date in the path, or a last segment that is a slug of three words, has five digits in a row, is an opaque id (eight or more letters and digits, three of them digits) or is a page file (`story.html`). The headline rule: 16 to 250 characters and three words, counted in characters so an emoji is one; or, with four characters of a script written without spaces (Thai, Lao, Myanmar, Khmer, Chinese, Japanese, Korean), six characters; not "Read more" and the like. The heading inside a card-wrapping anchor is the title. With three or more preferred links only those are returned. A link's date is a `<time datetime>` inside the anchor, or the one in the `<article>` or `<li>` around it when that element holds exactly one article link.
- **First-seen record.** `feed:seen:v1:<hex>` is `{ version: 1, seen: { <first 16 hex of SHA-256 of the link>: <Unix seconds first seen> } }`, read and written only when the site is really fetched (`withTimes` in `site-reader.ts`). A links-mode site records every article link on the page; a feed records only its items without a readable date (at most 100), and a feed whose items all have dates never touches KV for this. An item without a date of its own is returned with `published` = its first-seen time and `dateSource: "first_seen"`. The rules: (1) a link keeps its entry while it is still found, so an article that sits on a page for a month does not come back as new once its 7 days are over; entries for links no longer found are dropped after 30 days, and beyond 600 entries the oldest go first. (2) A link that is new to an existing record was first seen now. (3) When there is no record yet (nobody has fetched the site before), nothing says which links are new, so they are stamped 24 hours ago, one second apart in page order: a newly followed site shows in the history but does not push in above what other sites published today, and those links leave after 6 days. (4) When the record cannot be read, the links are stamped as in (3) but the record is not written (writing would replace every remembered time for good) and the site's result is not cached, so the next request tries again. (5) Two requests fetching the same site at once both write the record and the later write wins. KV expiry follows the real clock, so the tests check the stored timestamps and delete the site's cache entry to stand for the 30 minutes passing.
- **HTMLRewriter facts** (pinned by `api/test/html-rewriter.test.ts`): handlers run only while the transformed body is read; text comes in pieces that can split a character reference, not decoded; attribute values are not decoded; `onEndTag` throws for `<br>` or `<link>`; a self-closing `<a/>` or `<title/>` inside inline `<svg>` makes `onEndTag` throw as well, and a throw inside a handler ends the whole transform, so `onEndTag` is only called through `atEnd`, which treats such an element as ended at once (found by review, not by the first tests: a page with an icon link in its header returned no items); an element that is never closed gets its end call when an element around it closes, or never. So an open `<a>` is finished by the next `<a>` or at the end of the page, and `<main>` clears the count of open `<nav>` and `<footer>`. Name `HTMLRewriter` only inside a function: `src/app.ts` is loaded in Node by the spec writer.

- **Text that leaves the API.** Text from a site is shortened only with `cut` or `cutSource` (also never through a character reference such as `&amp;`), never a bare `.slice()`. `cut` ends on a grapheme cluster boundary, so a flag, a ZWJ family emoji, a skin tone, a keycap or a letter with its accents is never split: `Intl.Segmenter` (present in workerd; a test pins it) segments only 64 UTF-16 units either side of the cut, the window's first piece is not trusted, regional indicators are paired by counting back to the start of their run, and a cluster longer than the window is cut at a code point. `collapseSpace` removes C0 and C1 controls, zero-width space, direction marks (LRM, RLM and the Arabic letter mark U+061C) and the bidirectional embedding, override and isolate controls (U+202A to U+202E, U+2066 to U+2069), keeps the zero-width joiner and non-joiner that emoji sequences and some scripts need, and replaces a lone surrogate with U+FFFD. Both routes pass every title, source and excerpt through `wellFormed` once more on the way out, because a lone surrogate makes Swift's JSON decoding fail for the whole response.

An item dated more than 8 days ago is left out (the app shows 7; a day allowed for dates without a time). `interest` is the request's own string for a valid index or an exact (case-insensitive) match, else null. Each link once; 20 at most; and the route drops an item any of whose strings (title, link, source, excerpt, interest) holds any 8 consecutive characters of the key, case-sensitively (task 20; before, only the whole key): `keyRuns` puts the key's 8-character windows in a Set and `holdsKeyRun` looks up each 8-character slice of the text, so the work is linear in the text for any key length. Result pages are not fetched.
- **The key.** Read from `X-LLM-Key`; 16 to 512 characters of printable ASCII without spaces (`MIN_KEY_LENGTH`, `MAX_KEY_LENGTH`; this is also the header length cap), declared in the route so the spec and the Swift client carry it. It is put only into the chosen adapter's auth header (`x-api-key`, `Authorization: Bearer` or `x-goog-api-key`); never in a URL, a body, a log line, KV, an error or a thrown error's message. `callProvider` checks the URL is on the adapter's host before sending and does not follow redirects (a 3xx is `provider_error`), so the header cannot be carried elsewhere. Log lines are `discover: <provider> failed: <code>`, `discover: <provider> unexpected failure` or `discover: unexpected error` and nothing else. `api/test/discover.test.ts` runs, for all four adapters, a success with the key planted in the model text and the envelope plus every documented error, a redirect, a non-JSON error, a thrown error, an oversized body, a timeout and malformed requests, all echoing the key in bodies and headers, and asserts that no 8 consecutive characters of the key appear in any response or console call. The success plants five items on cited, undated pages, holding the whole key, only its tail, only its prefix, a run in the source and a run in the link; they are all dropped, and a control run under another key returns all five, so the check is not vacuous (also confirmed by putting the old whole-key filter back, which fails the test). Two more tests reach the 500 (an adapter throwing a `TypeError`, and `Intl.DateTimeFormat` throwing before the call), each with the key and an interest in the error's message, and assert the fixed body and the one fixed log line; that no KV method is called and no key appears, and that every outbound request went to the adapter's fixed URL (a probe confirmed a spy on the test's `env.CACHE` sees the Worker's KV calls). The timeout test shortens the deadline through `providerDeadline` in `http.ts`: fake timers cannot drive it, because the timer would abort a request from the test's context, which workerd refuses.
- **Not verified without a real key.** Every provider response in the tests is written by hand from the documentation, so these are unproven until someone runs a real call: whether each model accepts the exact request (Haiku 5.5 with `web_search_20250305` and `effort: "low"`; `gpt-6-luna` with `max_tool_calls` and `search_context_size`; `gemini-3.5-flash-lite` with `thinking_level: "low"` and whether `google_search_result` carries URLs on Interactions; Perplexity's `max_steps: 1` actually searching), whether the models follow the JSON instruction, how often their URLs match the citations, the real error bodies for quota (OpenAI's error pages give codes but no JSON body, so its fixtures use the usual `{ error: { message, type, param, code } }` envelope; Anthropic's ramp-limit message is invented around its documented code), whether real calls finish inside 25 s (a call that times out is still billed to the user), and whether returned links carry the provider's own tracking parameters (which would stop the app matching them against feed items).
