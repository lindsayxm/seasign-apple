# Architecture

Kept current by the lead session. The STACK section of `AGENTS.md` lists the chosen libraries; this file says how the parts fit together.

## Shape

```
iPhone app (ios/)  ──HTTPS, JSON──▶  API on Cloudflare Workers (api/)  ──▶  D1 (users, lists, follows)
   SwiftUI + SwiftData                  Hono + Zod + Better Auth        ──▶  KV (fetched news)
        ▲                                        │                      ◀──  Cron Trigger (morning refresh)
        └──── generated Swift client ◀── openapi/openapi.json ◀─────────┘
```

- **Business logic lives in the API** (weather and sun/moon, reading calendar links, fetching followed sites, AI search) so a later Android client can reuse it. The iOS app is UI plus local storage; it uses no location or calendar permission.
- **Signed out by default.** The v1 routes need no account: the app sends what the Worker needs with each request (zip, calendar links, site list, the user's LLM key) and keeps the user's data in SwiftData. Sign in with Apple and D1 sync come last (tasks 13 and 14).
- **User-supplied URLs** go through one safe-fetch helper in the Worker (https only, no private hosts, size and time caps). LLM keys and calendar links are never logged or stored; KV cache keys for calendars are hashes.
- **The OpenAPI spec is the contract.** It is generated from the Hono routes; the Swift client is generated from the spec. Neither is edited by hand.
- **Local first on the phone.** The UI reads SwiftData, then syncs from the API.
- **Auth.** Sign in with Apple on the device → Apple ID token → Better Auth → bearer session token in the Keychain. Every D1 query on user data is scoped by the session's user ID.

## How the pieces are wired

- **Spec to Swift.** `ios/project.yml` adds `openapi/openapi.json` and the generator config to the app target and runs the `OpenAPIGenerator` build plugin, so the Swift client is rebuilt from the spec on every build and never committed. After changing a route: `npm run openapi` in `api/`, then build the app. Both files sit in the Compile Sources phase so they are not shipped in the app; Xcode prints one harmless "no rule to process file" warning for each.
- **Command-line builds** need `-skipPackagePluginValidation` (XcodeBuildMCP: `extraArgs`), or the build plugin is refused. Use simulator IDs or exact names: iPhone 16 exists on iOS 18.3, iPhone 17 on iOS 27.2.
- **Simulators.** Build separately for each runtime: a Debug build made for the iOS 27.2 simulator does not launch on the 18.3 simulator, so build (or test) with the iPhone 16 selected before running there, and again with the iPhone 17. The UI automation tools can leave a simulator on the hardware keyboard, after which no on-screen keyboard appears; Simulator › I/O › Keyboard › Toggle Software Keyboard brings it back. XcodeBuildMCP keeps a test-products bundle of about 450 MB per test run under `~/Library/Developer/XcodeBuildMCP/workspaces/.../test-products`; clear old ones when disk is short.
- **Info.plist and fonts.** The app target has `info:` in `ios/project.yml`; XcodeGen writes `ios/Seasign/Info.plist` from it and Xcode merges the `INFOPLIST_KEY_*` build settings in at build time. The bundled fonts are listed there under `UIAppFonts` by file name; code refers to them by PostScript name (`FontName` in `Design/Typography.swift`), and `DesignTests` fails if a name does not load. `TARGETED_DEVICE_FAMILY: "1"` has to be on each target, because XcodeGen's iOS target preset sets `1,2` and beats a project-level value.
- **Caps.** Text is shown in capitals by `Text(caps:)`, which capitalises the string and keeps the original as the accessibility label; `.caps()` / `.capsRelative()` set only font and letter spacing. Do not use `textCase(.uppercase)`: it also capitalises accessibility labels, explicit ones included.
- **Local stores.** One `ModelContainer`, two SQLite files in Application Support (`LocalStore`): `default.store` holds what the user entered (`Settings`, `ListItem`; `SeasignSchema.userModels`) and `SkyCache.store` holds copies of API responses (`CachedSky`; `cacheModels`). If the container will not open, it is tried again with the cache in memory: when that works the user store is healthy, so only the cache file (with its `-wal` and `-shm`) is deleted and recreated, and if no cache file can be made the in-memory one serves for that launch. Every open uses the full schema, the configurations only route models to files (each file carries all three tables); opening `default.store` with fewer models would make Core Data migrate it. If the user store will not open, nothing is deleted and `StoreErrorView` offers Try again. Put a new model in `cacheModels` only if all of it can be fetched again. No migration plan is used; SwiftData's automatic lightweight migration covers added optional fields.
- **Scene rules** (all in `Scene/SkyMath.swift` and `SceneState.swift`, unit-tested). The sun and moon are placed from the rise and set instants on either side of now, not by pairing a date's rise with its set. The moon estimates a missing end with a 12.4 h arc; the sun never assumes a day length: with a sunrise or sunset missing, `isDay` decides unless a known sun event has happened since the reading. Discs take 15 minutes to rise out of and sink into the water (`SkyBodyState.placement`); the moon is drawn only when no part of the sun shows. A cached sky that covers today's date keeps placing sun and moon, but its temperature and weather are shown only within 3 hours of the fetch (`SkySnapshot.currentIsFresh`); a cache without today falls back to the neutral 06:00–18:00 scene. Redraw rate follows `SceneMotion`: 30 fps for rain, snow or wind, 10 fps for clouds, one redraw every 3 s on a clear night, one still frame otherwise or with Reduce Motion.
- **Debug launch arguments** (Debug builds only; read from `UserDefaults`, so they are passed as `-key value`, and the first three can also be set in Settings › Debug scene): `-debugTime sunrise|midday|sunset|night|moonrise|moonset`, optionally with an offset in minutes (`sunrise-5`, `sunset+7.5`, `moonset+8`); `-debugMoon 0…1` (phase; implies night); `-debugWeather clear|cloudy|windy|rain|snow`; `-debugStoreFailure YES` shows `StoreErrorView` without touching a store. Example: `xcrun simctl launch --terminate-running-process <udid> com.example.seasign -debugTime sunset+5 -debugWeather clear`.
- **Base URL.** Debug builds call `http://localhost:8787` (`npx wrangler dev` in `api/`). No App Transport Security exception is set; localhost loads on both the iOS 18.3 and iOS 27.2 Simulators without one. The Release URL is a placeholder until the Worker is deployed.
- **Spec writer.** `npm run openapi` runs `scripts/openapi.ts` with Node's type stripping, so imports inside `api/src` carry the `.ts` extension and `src/app.ts` must not import `cloudflare:*` modules.
- **Test runtime.** `@cloudflare/vitest-plugin` (the 1.x successor of `@cloudflare/vitest-pool-workers`; task 16) runs the tests in workerd. It pins exact `wrangler` and `miniflare` versions, so the tests and `wrangler dev` run the same workerd version (1.20261113.1 with plugin 1.8.2 and wrangler 4.162.0). `compatibility_date` in `api/wrangler.jsonc` must not be later than that workerd supports; it is 2026-11-13. Upgrade the plugin and wrangler together, then raise the date and rerun `npm run cf-typegen`.
- **Outbound fetch in tests.** Tests replace `globalThis.fetch` with `vi.spyOn(globalThis, "fetch").mockImplementation(...)` (see `mockOpenMeteo` in `api/test/sky.test.ts`): known hosts answer from `api/test/fixtures/`, any other request throws, and `afterEach` calls `vi.restoreAllMocks()`. Nothing reaches the network. Tests that need a fixed "now" fake only `Date` (`vi.useFakeTimers({ toFake: ["Date"] })`), so real timers such as the fetch deadline keep working; KV expiry still follows the real clock. `.ics` fixtures are imported as text with Vite's `?raw` suffix (`api/test/ics.d.ts`). Cloudflare's documented mechanism for the plugin is `@msw/cloudflare` with `msw` 3; neither is in STACK, so moving to it needs the user's approval.
- **KV keys.** `/v1/sky` caches in `CACHE`: `sky:geo:v1:<zip>` (place for a zip, 30 days) and `sky:forecast:v1:<zip>` (forecast, 15 minutes). The key builders are exported from `api/src/routes/sky.ts`. `/v1/calendar/events` caches each calendar's parsed occurrences under `cal:v1:<SHA-256 hex of the checked link>` for 15 minutes (`calendarCacheKey` in `api/src/routes/calendar.ts`); neither the key nor the value holds the link, and failures are not cached.
- **User-supplied URLs.** `safeFetch` in `api/src/lib/safe-fetch.ts` is the only way to fetch one (calendar links now; followed sites and AI-found pages in tasks 7 and 11). It reads `webcal://` as `https://`, then accepts https on port 443 only; refuses credentials in the URL, private, loopback, link-local and unique-local IP literals (IPv4, IPv6, and IPv4 carried inside IPv6), and local-only names (`localhost`, single-label hosts, `.local`, `.internal`, `.lan`, `.home.arpa` and the like); follows at most 3 redirects by hand and checks every hop the same way; holds one 8 second deadline across all hops and the body; counts the body while reading and stops at 2 MB whatever Content-Length says; sends `User-Agent: SeasignBot/1.0` and nothing else about the caller. It throws `SafeFetchError` with a `code`; the message is fixed text and never holds the URL. `parseSafeUrl` does the checks without fetching. It cannot stop a public name that resolves to a private address, because a Worker cannot resolve DNS before fetching.
- **Calendars.** `POST /v1/calendar/events` takes `{ links, timezone? }` as `application/json` (anything else, or a bad body, is the fixed 400 `invalid_request`). A link is a credential: it is never logged, stored or echoed, and calendars are named by their index in the request. Each link is fetched with `safeFetch` (once per request, whatever its spelling: links are de-duplicated by cache key) and parsed by `parseCalendar` (`api/src/lib/calendar.ts`) into the occurrences from one day back to eight days ahead: `instant` (Unix seconds), `floating` or `allDay` (wall-clock seconds, placed in the request's time zone when a request is answered). That list is cached; `upcomingEvents` filters it per request, so one cached copy serves any time zone. Each entry of `calendars` in the response has `ok`, `partial` and, on failure, `error`; `partial` is true when the calendar was read but something was left out (see below).
- **Calendar time zones.** Resolved in our code, in this order: the file's VTIMEZONE for that TZID; the IANA zone of that name through `Intl`; a Windows zone name through `WINDOWS_ZONES` (CLDR's windowsZones table, all 142 names, compared with CLDR main on 2026-11-15); otherwise the time is floating and the request's time zone decides. A VTIMEZONE is read from the parsed data by `readZone` and its offsets are worked out by `zoneOffset` (STANDARD and DAYLIGHT blocks with DTSTART, TZOFFSETFROM, TZOFFSETTO, RDATE and yearly RRULEs without COUNT); tests compare this with the IANA zones day by day over decades. `ICAL.TimezoneService` is isolate-global and must not be used.
- **ical.js only parses; nothing that repeats ever reaches it.** One call to ical.js's recurrence iterator cannot be interrupted, and rules exist that make it search for a date that never comes (`FREQ=MONTHLY;INTERVAL=48;BYDAY=5MO` from a February that is never in a leap year ran 45 s and more). It runs that iterator for an event's RRULE and, the first time a zone is used, for a VTIMEZONE's rules. A filter in front of it was got around three times (a rule shape the whitelist missed, twice; then a folded property name the text-level rename missed), so there is no filter any more. In `api/src/lib/calendar.ts`, ical.js (2.x) does two things: `ICAL.parse` turns the text into data, and its value classes decode a time, a duration or the parts of a rule. Then: (1) `cleanEvent` rebuilds every VEVENT from nine named properties with the value types expected of them, plus the event's rules as plain text under a name ical.js has no meaning for; alarms and anything nested are left behind. However a rule was written (case, fold, group, parameters, `VALUE=RECUR` on another property), it cannot arrive as a rule. (2) No VTIMEZONE is ever given to an ical.js object. (3) `readRule` and `expandRule` expand rules: the walk goes through the rule's periods (days, weeks, months or years) by index and works out each period's days with plain arithmetic. It ends for any rule, because each period starts later than the one before and the walk stops at the first period past the window. Without COUNT it starts at the window; with COUNT it counts from DTSTART. `api/test/calendar-smuggling.test.ts` replaces ical.js's iterator, zone expansion and offset methods with functions that throw and checks after every test that none was reached. Do not add a call to `ICAL.Event`, `RecurExpansion`, `Recur#iterator`, `Timezone#utcOffset` or `Time#toUnixTime` on file data.
- **Rules supported.** Daily, weekly, monthly, yearly with INTERVAL, COUNT, UNTIL, WKST, BYDAY, BYMONTHDAY, BYMONTH, BYSETPOS, in any letter case. Skipped (the calendar is then `partial`): rules finer than a day, BYHOUR and finer, BYWEEKNO, BYYEARDAY, a yearly rule with BYDAY or BYMONTHDAY but no BYMONTH, EXRULE, and any malformed rule. Lines are unfolded first (CRLF, LF or CR followed by a space or tab); then RRULE and EXRULE lines are renamed before `ICAL.parse`, only because ical.js decodes them while parsing and one malformed rule would otherwise reject the whole file. Where ical.js and RFC 5545 disagree we follow the RFC: DTSTART always counts as the first of COUNT; a monthly rule with INTERVAL and BYMONTH keeps to the interval's months; the last day of February stays in February; months without the day (the 31st, 29 February) are skipped. An UNTIL earlier than DTSTART leaves DTSTART alone. `RANGE=THISANDFUTURE` overrides change only their own instance. `EXDATE;VALUE=DATE` on a timed series removes that local day. A file may hold several VCALENDARs (20 are read). A VEVENT or VTIMEZONE nested in another component is not read and sets `partial`.
- **Calendar CPU limits.** A calendar file is untrusted input. (1) Every loop over a repeat rule or a zone's rules is ours and is charged to a work budget per file (`MAX_WORK_PER_FILE`); when it runs out, reading stops and the calendar is `partial`. (2) A VTIMEZONE may have 60 blocks, 12 rules and 400 listed dates, and a file 50 zones; a zone's changes are worked out a year at a time and only for times within three days of the kept window. (3) Every time zone lookup is charged to the budget too (10 units), a file may name 50 distinct TZIDs it does not define (`Intl` accepts any capitalisation and builds a formatter per spelling; later names are read as floating), and a series that began long ago is not looked up at all. (4) The VEVENTs are put into a component of their own under an otherwise empty calendar: for each time with a TZID, ical.js searches all the calendar's children for a VTIMEZONE, which took 8 s for 30,000 events. (5) An event listing more than 2,000 EXDATE and RDATE values is skipped. (6) At most 500 occurrences are kept per calendar. `Date.now()` does not advance during CPU work in a Worker, so a time budget would not work. Measured in Node on files of 1 to 3 MB (the fetch cap is 2 MB): of twelve hostile or very large files the slowest takes about 0.35 s (9,000 yearly rules over all twelve months with COUNT, from 1900).
