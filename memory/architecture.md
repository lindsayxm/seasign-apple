# Architecture

Kept current by the lead session. The STACK section of `AGENTS.md` lists the chosen libraries; this file says how the parts fit together.

## Shape

```
iPhone app (ios/)  ──HTTPS, JSON──▶  API on Cloudflare Workers (api/)  ──▶  D1 (users, lists, follows)
   SwiftUI + SwiftData                  Hono + Zod + Better Auth        ──▶  KV (fetched news)
        ▲                                        │                      ◀──  Cron Trigger (morning refresh)
        └──── generated Swift client ◀── openapi/openapi.json ◀─────────┘
```

- **Business logic lives in the API** (weather and sun/moon, reading calendar links, fetching followed sites, AI search) so a later Android client can reuse it. The iOS app is UI plus local storage; it uses no location or calendar permission.
- **Signed out by default.** The v1 routes need no account: the app sends what the Worker needs with each request (zip, calendar links, site list, the user's LLM key) and keeps the user's data in SwiftData. Sign in with Apple and D1 sync come last (tasks 13 and 14).
- **User-supplied URLs** go through one safe-fetch helper in the Worker (https only, no private hosts, size and time caps). LLM keys and calendar links are never logged or stored; KV cache keys for calendars are hashes.
- **The OpenAPI spec is the contract.** It is generated from the Hono routes; the Swift client is generated from the spec. Neither is edited by hand.
- **Local first on the phone.** The UI reads SwiftData, then syncs from the API.
- **Auth.** Sign in with Apple on the device → Apple ID token → Better Auth → bearer session token in the Keychain. Every D1 query on user data is scoped by the session's user ID.

## How the pieces are wired

- **Spec to Swift.** `ios/project.yml` adds `openapi/openapi.json` and the generator config to the app target and runs the `OpenAPIGenerator` build plugin, so the Swift client is rebuilt from the spec on every build and never committed. After changing a route: `npm run openapi` in `api/`, then build the app. Both files sit in the Compile Sources phase so they are not shipped in the app; Xcode prints one harmless "no rule to process file" warning for each.
- **Command-line builds** need `-skipPackagePluginValidation` (XcodeBuildMCP: `extraArgs`), or the build plugin is refused. Use simulator IDs or exact names: iPhone 16 exists on iOS 18.3, iPhone 17 on iOS 27.2.
- **Simulators.** Build separately for each runtime: a Debug build made for the iOS 27.2 simulator does not launch on the 18.3 simulator, so build (or test) with the iPhone 16 selected before running there, and again with the iPhone 17. The UI automation tools can leave a simulator on the hardware keyboard, after which no on-screen keyboard appears; Simulator › I/O › Keyboard › Toggle Software Keyboard brings it back. XcodeBuildMCP keeps a test-products bundle of about 450 MB per test run under `~/Library/Developer/XcodeBuildMCP/workspaces/.../test-products`; clear old ones when disk is short.
- **Info.plist and fonts.** The app target has `info:` in `ios/project.yml`; XcodeGen writes `ios/Seasign/Info.plist` from it and Xcode merges the `INFOPLIST_KEY_*` build settings in at build time. The bundled fonts are listed there under `UIAppFonts` by file name; code refers to them by PostScript name (`FontName` in `Design/Typography.swift`), and `DesignTests` fails if a name does not load. `TARGETED_DEVICE_FAMILY: "1"` has to be on each target, because XcodeGen's iOS target preset sets `1,2` and beats a project-level value.
- **Caps.** Text is shown in capitals by `Text(caps:)`, which capitalises the string and keeps the original as the accessibility label; `.caps()` / `.capsRelative()` set only font and letter spacing. Do not use `textCase(.uppercase)`: it also capitalises accessibility labels, explicit ones included.
- **Local stores.** One `ModelContainer`, two SQLite files in Application Support (`LocalStore`): `default.store` holds what the user entered (`Settings`, `ListItem`, `CalendarLink`; `SeasignSchema.userModels`) and `SkyCache.store` holds copies of API responses (`CachedSky`, `CachedEvents`; `cacheModels`). If the container will not open, it is tried again with the cache in memory: when that works the user store is healthy, so only the cache file (with its `-wal` and `-shm`) is deleted and recreated, and if no cache file can be made the in-memory one serves for that launch. Every open uses the full schema, the configurations only route models to files (each file carries every model's table); opening `default.store` with fewer models would make Core Data migrate it. If the user store will not open, nothing is deleted and `StoreErrorView` offers Try again. Put a new model in `cacheModels` only if all of it can be fetched again. No migration plan is used; SwiftData's automatic lightweight migration covers added optional fields and added models (task 6 added `CalendarLink` and `CachedEvents`; `LocalStoreTests` opens stores written with the earlier schema and checks nothing is lost and the cache file is kept).
- **Scene rules** (all in `Scene/SkyMath.swift` and `SceneState.swift`, unit-tested). The sun and moon are placed from the rise and set instants on either side of now, not by pairing a date's rise with its set. The moon estimates a missing end with a 12.4 h arc; the sun never assumes a day length: with a sunrise or sunset missing, `isDay` decides unless a known sun event has happened since the reading. Discs take 15 minutes to rise out of and sink into the water (`SkyBodyState.placement`); the moon is drawn only when no part of the sun shows. A cached sky that covers today's date keeps placing sun and moon, but its temperature and weather are shown only within 3 hours of the fetch (`SkySnapshot.currentIsFresh`); a cache without today falls back to the neutral 06:00–18:00 scene. Redraw rate follows `SceneMotion`: 30 fps for rain, snow or wind, 10 fps for clouds, one redraw every 3 s on a clear night, one still frame otherwise or with Reduce Motion.
- **Debug launch arguments** (Debug builds only; read from `UserDefaults`, so they are passed as `-key value`, and the first three can also be set in Settings › Debug scene): `-debugTime sunrise|midday|sunset|night|moonrise|moonset`, optionally with an offset in minutes (`sunrise-5`, `sunset+7.5`, `moonset+8`); `-debugMoon 0…1` (phase; implies night); `-debugWeather clear|cloudy|windy|rain|snow`; `-debugStoreFailure YES` shows `StoreErrorView` without touching a store; `-debugEvents YES` shows two sample calendar links and three sample events from a store in memory (`EventsModel.sample`), fetching nothing and leaving the user's store alone. Example: `xcrun simctl launch --terminate-running-process <udid> com.example.seasign -debugTime sunset+5 -debugWeather clear`.
- **Calendar links on the phone.** A link is a credential. It is stored only in `CalendarLink.url` (user store) and sent only in the body of `POST /v1/calendar/events`. Nothing else may hold it: `SeasignAPI.calendarEvents` drops the generated client's error (its description includes the request) and throws a payload-free `CalendarFailure`; messages come from fixed text (`LinkProblem.message`, `EventsModel.AddProblem.message`); Settings shows the name and `LinkMask.host(of:)` (the last two labels of the host, three for `co.uk`-style suffixes); the cache (`CachedEvents`, a JSON `EventsSnapshot`) ties events and per-link status to `CalendarLink.id`. Do not interpolate a `CalendarLink` or its `url` into a string, a log or an accessibility label. The app imports no EventKit and has no calendar usage string (`NoCalendarPermissionTests`).
- **Events on Today.** `EventsModel` (in the environment next to `TodayModel`) loads the links and the cached snapshot at launch, and `refresh()` runs at launch, every minute while Today is open, on return to the foreground and when the events' time zone changes; a snapshot younger than 10 minutes that covers every link is not fetched again. The time zone is `EventZone.resolve`: the zip's zone when a zip is set and its sky is known, otherwise the phone's. It is sent as `timezone` and used for formatting. A snapshot made for another zone is dropped and refetched, because all-day events were placed in the zone they were asked for. Adding a link asks the API for that one link (the check and its events in one request); a failed link is not saved. A whole-request failure keeps what is on screen. Per link: a failure shows only in Settings; events of a link that failed with `fetch_failed` or `timeout` are carried over from the previous snapshot until they end; any other failure drops them. Removing a link drops its events at once.
- **Which events and how they read** (`EventPicker`, `EventLabel`; pure, unit-tested). Not ended by the API's rule (an event without a length is over once it has started), soonest first, all-day before timed at the same instant, three at most; the Today clock tick drops events as they end. Time is `10:15AM` (12-hour, built by hand, so the device's 24-hour setting does not change it); all-day events read `ALL DAY` and belong to their `date` string whatever the zone; an event starting on a later day gets the day first (`TUE 9:00AM`, `TUE ALL DAY`), one that began before today and is still running does not; an empty title reads `No title`. `EventsColumn` shows as many of the three as fit above the header rule; the "set your zip" prompt stands alone when there are no events and goes under the events only if it fits.
- **Base URL.** Debug builds call `http://localhost:8787` (`npx wrangler dev` in `api/`). No App Transport Security exception is set; localhost loads on both the iOS 18.3 and iOS 27.2 Simulators without one. The Release URL is a placeholder until the Worker is deployed.
- **Spec writer.** `npm run openapi` runs `scripts/openapi.ts` with Node's type stripping, so imports inside `api/src` carry the `.ts` extension and `src/app.ts` must not import `cloudflare:*` modules.
- **Test runtime.** `@cloudflare/vitest-plugin` (the 1.x successor of `@cloudflare/vitest-pool-workers`; task 16) runs the tests in workerd. It pins exact `wrangler` and `miniflare` versions, so the tests and `wrangler dev` run the same workerd version (1.20261113.1 with plugin 1.8.2 and wrangler 4.162.0). `compatibility_date` in `api/wrangler.jsonc` must not be later than that workerd supports; it is 2026-11-13. Upgrade the plugin and wrangler together, then raise the date and rerun `npm run cf-typegen`.
- **Outbound fetch in tests.** Tests replace `globalThis.fetch` with `vi.spyOn(globalThis, "fetch").mockImplementation(...)` (see `mockOpenMeteo` in `api/test/sky.test.ts`): known hosts answer from `api/test/fixtures/`, any other request throws, and `afterEach` calls `vi.restoreAllMocks()`. Nothing reaches the network. Tests that need a fixed "now" fake only `Date` (`vi.useFakeTimers({ toFake: ["Date"] })`), so real timers such as the fetch deadline keep working; KV expiry still follows the real clock. `.ics` fixtures are imported as text with Vite's `?raw` suffix (`api/test/ics.d.ts`). Cloudflare's documented mechanism for the plugin is `@msw/cloudflare` with `msw` 3; neither is in STACK, so moving to it needs the user's approval.
- **KV keys.** `/v1/sky` caches in `CACHE`: `sky:geo:v1:<zip>` (place for a zip, 30 days) and `sky:forecast:v1:<zip>` (forecast, 15 minutes). The key builders are exported from `api/src/routes/sky.ts`. `/v1/calendar/events` caches each calendar's parsed occurrences under `cal:v1:<SHA-256 hex of the checked link>` for 15 minutes (`calendarCacheKey` in `api/src/routes/calendar.ts`); neither the key nor the value holds the link, and failures are not cached. `/v1/feed` caches each site's items under `feed:site:v1:<SHA-256 hex>` for 30 minutes and, for a links-mode site, keeps `feed:seen:v1:<the same hex>` for 30 days (`siteCacheKey`, `seenCacheKey` in `api/src/lib/site-reader.ts`). The hash is over the mode, the checked page URL and, in feed mode, the checked feed URL: the endpoint is open, so without the feed URL in it anyone could fill a well-known page's entry from a feed of their own. Keys hold no part of a URL; the cached items hold the articles' own links, never the page or feed address.
- **User-supplied URLs.** `safeFetch` in `api/src/lib/safe-fetch.ts` is the only way to fetch one (calendar links, followed sites and their feeds; AI-found pages in task 11). It reads `webcal://` as `https://`, then accepts https on port 443 only; refuses credentials in the URL, private, loopback, link-local and unique-local IP literals (IPv4, IPv6, and IPv4 carried inside IPv6), and local-only names (`localhost`, single-label hosts, `.local`, `.internal`, `.lan`, `.home.arpa` and the like); follows at most 3 redirects by hand and checks every hop the same way; holds one 8 second deadline across all hops and the body; counts the body while reading and stops at 2 MB whatever Content-Length says; sends `User-Agent: SeasignBot/1.0` and nothing else about the caller. It throws `SafeFetchError` with a `code`; the message is fixed text and never holds the URL. `parseSafeUrl` does the checks without fetching. It cannot stop a public name that resolves to a private address, because a Worker cannot resolve DNS before fetching.
- **Calendars.** `POST /v1/calendar/events` takes `{ links, timezone? }` as `application/json` (anything else, or a bad body, is the fixed 400 `invalid_request`). A link is a credential: it is never logged, stored or echoed, and calendars are named by their index in the request. Each link is fetched with `safeFetch` (once per request, whatever its spelling: links are de-duplicated by cache key) and parsed by `parseCalendar` (`api/src/lib/calendar.ts`) into the occurrences from one day back to eight days ahead: `instant` (Unix seconds), `floating` or `allDay` (wall-clock seconds, placed in the request's time zone when a request is answered). That list is cached; `upcomingEvents` filters it per request, so one cached copy serves any time zone. Each entry of `calendars` in the response has `ok`, `partial` and, on failure, `error`; `partial` is true when the calendar was read but something was left out (see below).
- **Calendar time zones.** Resolved in our code, in this order: the file's VTIMEZONE for that TZID; the IANA zone of that name through `Intl`; a Windows zone name through `WINDOWS_ZONES` (CLDR's windowsZones table, all 142 names, compared with CLDR main on 2026-11-15); otherwise the time is floating and the request's time zone decides. A VTIMEZONE is read from the parsed data by `readZone` and its offsets are worked out by `zoneOffset` (STANDARD and DAYLIGHT blocks with DTSTART, TZOFFSETFROM, TZOFFSETTO, RDATE and yearly RRULEs without COUNT); tests compare this with the IANA zones day by day over decades. `ICAL.TimezoneService` is isolate-global and must not be used.
- **ical.js only parses; nothing that repeats ever reaches it.** One call to ical.js's recurrence iterator cannot be interrupted, and rules exist that make it search for a date that never comes (`FREQ=MONTHLY;INTERVAL=48;BYDAY=5MO` from a February that is never in a leap year ran 45 s and more). It runs that iterator for an event's RRULE and, the first time a zone is used, for a VTIMEZONE's rules. A filter in front of it was got around three times (a rule shape the whitelist missed, twice; then a folded property name the text-level rename missed), so there is no filter any more. In `api/src/lib/calendar.ts`, ical.js (2.x) does two things: `ICAL.parse` turns the text into data, and its value classes decode a time, a duration or the parts of a rule. Then: (1) `cleanEvent` rebuilds every VEVENT from nine named properties with the value types expected of them, plus the event's rules as plain text under a name ical.js has no meaning for; alarms and anything nested are left behind. However a rule was written (case, fold, group, parameters, `VALUE=RECUR` on another property), it cannot arrive as a rule. (2) No VTIMEZONE is ever given to an ical.js object. (3) `readRule` and `expandRule` expand rules: the walk goes through the rule's periods (days, weeks, months or years) by index and works out each period's days with plain arithmetic. It ends for any rule, because each period starts later than the one before and the walk stops at the first period past the window. Without COUNT it starts at the window; with COUNT it counts from DTSTART. `api/test/calendar-smuggling.test.ts` replaces ical.js's iterator, zone expansion and offset methods with functions that throw and checks after every test that none was reached. Do not add a call to `ICAL.Event`, `RecurExpansion`, `Recur#iterator`, `Timezone#utcOffset` or `Time#toUnixTime` on file data.
- **Rules supported.** Daily, weekly, monthly, yearly with INTERVAL, COUNT, UNTIL, WKST, BYDAY, BYMONTHDAY, BYMONTH, BYSETPOS, in any letter case. Skipped (the calendar is then `partial`): rules finer than a day, BYHOUR and finer, BYWEEKNO, BYYEARDAY, a yearly rule with BYDAY or BYMONTHDAY but no BYMONTH, EXRULE, and any malformed rule. Before `ICAL.parse`, lines are unfolded (CRLF, LF or CR followed by a space or tab) and `readableLines` reduces the file to what the reader uses: BEGIN and END, twelve named properties with only their TZID, RANGE and date-typed VALUE parameters, and RRULE/EXRULE renamed to plain text. This is for robustness and speed, not safety: ical.js rejects a whole file for one value it cannot decode (a malformed rule, or any value marked `VALUE=RECUR` or `VALUE=PERIOD`) and takes 2 to 3 s over a line with 200,000 parameters. A line that is not a property at all is left out and sets `partial`. Where ical.js and RFC 5545 disagree we follow the RFC: DTSTART always counts as the first of COUNT; a monthly rule with INTERVAL and BYMONTH keeps to the interval's months; the last day of February stays in February; months without the day (the 31st, 29 February) are skipped. An UNTIL earlier than DTSTART leaves DTSTART alone. `RANGE=THISANDFUTURE` overrides change only their own instance. `EXDATE;VALUE=DATE` on a timed series removes that local day. A file may hold several VCALENDARs (20 are read). A VEVENT or VTIMEZONE nested in another component is not read and sets `partial`.
- **Calendar CPU limits.** A calendar file is untrusted input. (1) Every loop over a repeat rule or a zone's rules is ours and is charged to a work budget per file (`MAX_WORK_PER_FILE`); when it runs out, reading stops and the calendar is `partial`. (2) A VTIMEZONE may have 60 blocks, 12 rules and 400 listed dates, and a file 50 zones; a zone's changes are worked out a year at a time and only for times within three days of the kept window. (3) Every time zone lookup is charged to the budget too (10 units), a file may name 50 distinct TZIDs it does not define (`Intl` accepts any capitalisation and builds a formatter per spelling; later names are read as floating), and a series that began long ago is not looked up at all. (4) The VEVENTs are put into a component of their own under an otherwise empty calendar: for each time with a TZID, ical.js searches all the calendar's children for a VTIMEZONE, which took 8 s for 30,000 events. (5) An event listing more than 2,000 EXDATE and RDATE values is skipped. (6) At most 500 occurrences are kept per calendar. `Date.now()` does not advance during CPU work in a Worker, so a time budget would not work. Measured in Node on files of 1 to 3 MB (the fetch cap is 2 MB): of twelve hostile or very large files the slowest takes about 0.35 s (9,000 yearly rules over all twelve months with COUNT, from 1900).
- **npm.** npm 10.9.2 crashed while resolving Vitest 4's peers during tasks 2 and 3, and `npx -y npm@11 install ...` was the workaround. In task 16 a plain `npm install` with 10.9.2 swapped the test package without crashing, in task 5 it installed `ical.js` without crashing, and in task 7 `fast-xml-parser` (5.12.1) likewise; it reports 4 moderate audit advisories, left alone. Try the installed npm first; `npm ci` against the lockfile works.
- **Followed sites.** The app stores `{ url, mode, feedUrl? }` per site and sends the list with each `/v1/feed` request; the API keeps nothing about a user. A site address is never logged or put in an error (log lines carry the index and a code), though it is not a credential. `POST /v1/sites/resolve` takes `{ url }`, fetches the page and answers 200 with `{ ok: true, title, url, mode, feedUrl?, linkCount? }` or `{ ok: false, error }`; `url` is the typed address in normal form, not the redirect target. An address that is itself a feed gives mode `feed` with that address and no `linkCount`. For a web page, `linkCount` is how many article links the page shows now (at most 200), so the app can warn when links mode would give nothing. The page's `<link rel="alternate">` feeds (RSS, Atom and RDF types; `text/xml` or `application/xml` only when the title or address says rss, atom or feed; never a `rel` that includes `stylesheet`) are resolved against the answering address and `<base>`, checked with the safe-URL rules, and ordered: not a comments feed, then most leading path segments shared with the page, then document order. Which are asked for: on a site's front page, or on a page with no article links, any of them; on any other page only feeds that share the page's first path segment, because a feed that shares nothing is most likely the whole site's and would bring in every section (the live check below is where this came from). At most two are fetched and the first that answers with a real feed wins; otherwise the mode is `links`. A feed on another host (a feed service) shares no path, so a section page whose only feed is hosted elsewhere is followed by its links. What a response is (`bodyKind`) goes by its first element before its Content-Type, because feeds are served as `text/html` and pages as `text/plain`; leading comments and processing instructions are stepped over, not searched, so `<!-- <rss> -->` in front of a page does not make it a feed.
- **`POST /v1/feed`.** Body `{ sites: [{ url, mode, feedUrl? }] }`, 1 to 50; a bad body or a body not sent as `application/json` is the fixed 400 `invalid_request`. The answer is `{ items, sites: [{ index, ok, error? }] }`; one failing site does not fail the rest, failures are not cached, and mode `feed` without `feedUrl` is that site's `invalid_url`. An item has `site` (index), `title`, `link`, `source`, `published` (UTC, second precision, never null), `dateSource` (`published` or `first_seen`) and `excerpt` (plain text, at most 300 characters, or null; always null in links mode). Every item has a time, so every item ages out: the 7-day window is applied when a site is fetched and again on every answer, and a cached site never returns an item that has aged out. A date up to a day ahead of the clock counts as now; later than that, the item is left out. An item with no readable date of its own, on a page or in a feed, gets a first-seen time (below). Order: newest first, then site index, then the site's own order. At most 30 items per site and 300 in all. A link is returned once, under the lowest site index that has it. Sites that are not in the cache are fetched 6 at a time, 6 seconds each, inside 20 seconds for the whole request (`performance.now()`, which like `Date.now()` moves with I/O in a Worker); a site not started by then is `timeout`. A site sent twice is read once. The cached value is `{ version: 2, source, items }`.
- **Feeds (`api/src/lib/feed-parse.ts`).** fast-xml-parser 5 with `preserveOrder` (so text, CDATA and nested XHTML keep their order), `processEntities: false` and `maxNestedTags: 64`. Before the parser sees the text, `checkShape` reads it once and refuses (`not_feed`) what the parser cannot hold in memory or should not see: more than 1 MB; a tag longer than 8,192 characters; more than 64 attributes on an element or processing instruction, counted with a copy of the parser's own attribute pattern (`attrsRegx`), which quotes do not stop, so `<x "a0='' a1='' …"/>` counts every pair inside the quotes as the parser does; more than 60,000 tags, comments, CDATA sections and processing instructions together; a run of text longer than 131,072 characters (`MAX_TEXT_RUN`; the parser builds text one character at a time and starts a new string only at a tag, a processing instruction or CDATA, so text either side of a comment or the DOCTYPE is one run, and so is text before the first tag or after the last; CDATA is taken in one piece and is not limited); a `<` that does not start one of those (`< `, `<<`); anything left unclosed; any declaration but one DOCTYPE (any letter case); and a DOCTYPE with an internal subset or any `<` inside it, which is where entities (billion laughs, external entities) are defined. It finds the end of each piece the way the parser does (quotes hide a `>` in an opening tag and a processing instruction, not in a closing tag; comments and CDATA are skipped whole), so a small tag there is a small tag here; re-read `readTagExp`, `tagExpWithClosingIndex`, `attrsRegx`, where `textData` is reset in `parseXml`, and `DocTypeReader.readDocType` when upgrading fast-xml-parser. The DOCTYPE that passes is cut out of the text before the parser sees it: it declares nothing we use, and the parser reads only an upper-case `<!DOCTYPE` as one (a lower-case `<!doctype rss>` became an element holding the whole feed, so the feed had no root). The parser also expands no entity, so a reference the document leaves undefined stays as written; our `decodeEntities` handles the XML five, numeric references and common HTML names, and cannot make text longer. Nesting past 64 or an element named `constructor` or `__proto__` makes the parser throw; every throw becomes `FeedParseError` without the parser's message, which quotes the input. A document is a feed by its root element (`rss` with a `channel`, `rdf:RDF`, `feed`), not by having parsed: HTML often parses. Dates are read by two anchored patterns on the first 64 characters (ISO 8601 / RFC 3339 and RFC 822), never by `Date.parse`, which accepts things like `"12"`. RFC 822 dates may leave out the space after the weekday's comma, may leave out the time (`Sat, 14 Nov 2026` is midnight UTC) and may end in a comment (`+0000 (UTC)`); the zone is an offset, GMT/UTC/UT with an offset (`GMT+1`, `UTC+01:00`, `GMT-0530`, read as that far east of UTC), or a name: about fifty zone names are known (where a name is ambiguous the common reading is taken: CST and EST North American, IST India) and an unknown name is read as UTC, since a date a few hours out is better than none; no zone means UTC. Any year the patterns can read counts, 0000 to 9999: a date before the 7-day window is old and the item is dropped (Hugo writes `Mon, 01 Jan 0001` for undated pages, which used to be read as no date and so got a first-seen time and showed as new), and one more than a day ahead is left out like any other future date (in links mode such a link gets a first-seen time, as before). Links are resolved against the answering address and `xml:base` (root, channel, item or entry, link), `http:` is read as `https:`, and each must pass `assertSafeUrl` or the item is dropped. RSS `description` and Atom `type="html"` are HTML written as text: escaped text is unescaped once, CDATA is taken as written, then `htmlToText` strips it.
- **Pages without a feed (`api/src/lib/page-links.ts`).** HTMLRewriter collects every `<a href>` with its text, whether it sits in `<nav>`/`<footer>`, and whether it is "preferred" (inside `<article>`, `<main>` or an h1-h3, or wrapping one). `articleLinks` keeps a link when it is outside nav and footer; resolves to a safe https URL on the page's host (same host name ignoring a leading `www.`; there is no public-suffix list, so other subdomains do not count); has an article-like address; and has headline-length text. The address rule (`isArticlePath`), in order: the page itself or a page above it is out unless its query names an article (`/index.php?p=77` from `/index.php?cat=2`; the parameters are `id`, `p`, `article`, `story`, `post`, `item` and their `...id` forms); a file that is not a page (`.pdf`, `.jpg`) is out; after the part of the path shared with the page, a segment naming something else (sign-in, search, about, `page/2`, `index.html`) puts it out, and a `tag`, `author` or `category` segment is allowed only with a date in the path (`/category/tech/2026/11/15/a-story`) or two more segments ending in a slug; then one of these must hold: an article query, more segments than the page, a date in the path, or a last segment that is a slug of three words, has five digits in a row, is an opaque id (eight or more letters and digits, three of them digits) or is a page file (`story.html`). The headline rule: 16 to 250 characters and three words, counted in characters so an emoji is one; or, with four characters of a script written without spaces (Thai, Lao, Myanmar, Khmer, Chinese, Japanese, Korean), six characters; not "Read more" and the like. The heading inside a card-wrapping anchor is the title. With three or more preferred links only those are returned. A link's date is a `<time datetime>` inside the anchor, or the one in the `<article>` or `<li>` around it when that element holds exactly one article link.
- **First-seen record.** `feed:seen:v1:<hex>` is `{ version: 1, seen: { <first 16 hex of SHA-256 of the link>: <Unix seconds first seen> } }`, read and written only when the site is really fetched (`withTimes` in `site-reader.ts`). A links-mode site records every article link on the page; a feed records only its items without a readable date (at most 100), and a feed whose items all have dates never touches KV for this. An item without a date of its own is returned with `published` = its first-seen time and `dateSource: "first_seen"`. The rules: (1) a link keeps its entry while it is still found, so an article that sits on a page for a month does not come back as new once its 7 days are over; entries for links no longer found are dropped after 30 days, and beyond 600 entries the oldest go first. (2) A link that is new to an existing record was first seen now. (3) When there is no record yet (nobody has fetched the site before), nothing says which links are new, so they are stamped 24 hours ago, one second apart in page order: a newly followed site shows in the history but does not push in above what other sites published today, and those links leave after 6 days. (4) When the record cannot be read, the links are stamped as in (3) but the record is not written (writing would replace every remembered time for good) and the site's result is not cached, so the next request tries again. (5) Two requests fetching the same site at once both write the record and the later write wins. KV expiry follows the real clock, so the tests check the stored timestamps and delete the site's cache entry to stand for the 30 minutes passing.
- **HTMLRewriter facts** (pinned by `api/test/html-rewriter.test.ts`): handlers run only while the transformed body is read; text comes in pieces that can split a character reference, not decoded; attribute values are not decoded; `onEndTag` throws for `<br>` or `<link>`; a self-closing `<a/>` or `<title/>` inside inline `<svg>` makes `onEndTag` throw as well, and a throw inside a handler ends the whole transform, so `onEndTag` is only called through `atEnd`, which treats such an element as ended at once (found by review, not by the first tests: a page with an icon link in its header returned no items); an element that is never closed gets its end call when an element around it closes, or never. So an open `<a>` is finished by the next `<a>` or at the end of the page, and `<main>` clears the count of open `<nav>` and `<footer>`. Name `HTMLRewriter` only inside a function: `src/app.ts` is loaded in Node by the spec writer.
- **Site and feed limits.** Request bodies: 64 KB on every `/v1/*` route (`MAX_BODY_BYTES`, a small middleware of our own in `src/app.ts`), counted byte by byte as the body is read, before any JSON is parsed, and the routes read the counted copy. Content-Length is used only to refuse early when it says more than the limit; a header that says less, or is not a number, does not let a larger body through (Hono's `bodyLimit`, used before, trusted the header when there was one: in process a 3 MB body sent with `content-length: 10` was read whole); over it is the 400 `{ error: "invalid_request", message: "The request body is too large" }`. A 50-site `/v1/feed` request with ordinary addresses is about 10 KB. Fetched bodies through `safeFetch`: pages 2 MB, feeds 1 MB (ordinary feeds are 20 to 700 KB; podcast-style feeds with hundreds of full-text items are larger and are refused as `too_large`). Feed: the `checkShape` limits above, 500 items scanned, 2,000 children per element looked at, 40,000 characters per field before stripping, title 300, excerpt 300, source 120 characters, link 2,048. Page: 1,500 `<a href>` scanned, 40,000 handler calls (HTMLRewriter cannot be stopped, so the page is fed to it 16 KB at a time and the feeding stops once the count or the link limit is reached; before this, 100,000 headings inside one link took 2.2 s), 200 article links kept, 600 characters of anchor text, 20 advertised feeds. `htmlToText` scans at most 40,000 characters. Nothing in `text.ts` runs a regular expression over input except single character classes.
- **Text that leaves the API.** Text from a site is shortened only with `cut` or `cutSource` (also never through a character reference such as `&amp;`), never a bare `.slice()`. `cut` ends on a grapheme cluster boundary, so a flag, a ZWJ family emoji, a skin tone, a keycap or a letter with its accents is never split: `Intl.Segmenter` (present in workerd; a test pins it) segments only 64 UTF-16 units either side of the cut, the window's first piece is not trusted, regional indicators are paired by counting back to the start of their run, and a cluster longer than the window is cut at a code point. `collapseSpace` removes C0 and C1 controls, zero-width space, direction marks (LRM, RLM and the Arabic letter mark U+061C) and the bidirectional embedding, override and isolate controls (U+202A to U+202E, U+2066 to U+2069), keeps the zero-width joiner and non-joiner that emoji sequences and some scripts need, and replaces a lone surrogate with U+FFFD. Both routes pass every title, source and excerpt through `wellFormed` once more on the way out, because a lone surrogate makes Swift's JSON decoding fail for the whole response.
- **Measured time** (about the largest input each path accepts, best of three). Text helpers in workerd, slowest 71 ms (2 MB of `&`). Feed parser in Node on 1 MB feeds built to sit just inside the `checkShape` limits, module loading not counted: slowest 176 ms (59,000 elements with distinct names), 3,200 elements of 64 distinct attributes 145 ms, 59,000 one-character text nodes 108 ms; what is over a limit is refused by one pass over the text in about 1 ms. Since attributes are counted with the parser's pattern (final round of task 7), that pass costs up to about 20 ms on 1 MB made of tags full of attributes: 13 ms for 2,000 elements of 64 attributes (82 ms for the whole `parseFeed`), 20 ms for 120 tags of 8 KB of bare words. Page reader in workerd: slowest 257 ms (200,000 headings inside one link), 33,000 advertised feeds 142 ms. By arithmetic, not measurement, a request of 50 such sites would cost about 10 s of CPU.
- **Workers plan.** Cloudflare's limits page (read 2026-11-15) gives the Free plan 10 ms of CPU per request and 50 subrequests to outside hosts (every redirect hop counts; KV calls count against a separate 1,000), and the Paid plan 30 s of CPU by default and 10,000 subrequests. So `/v1/feed` cannot run on the Free plan: one ordinary feed takes more than 10 ms to parse, and 50 sites with redirects pass 50 subrequests. `limits.cpu_ms` in `api/wrangler.jsonc` can cap a request's CPU below 30 s. The per-IP rate limit the plan calls for is not built yet.
- **Measured memory.** A Worker isolate has 128 MB; the local workerd does not enforce it, so the tests cannot fail on memory and assert refusal instead. Feed parser, in Node 22 with `--max-old-space-size` lowered until the parse dies. The parser alone, without `checkShape`, on 2 MB (first review round): `< ` repeated and closed by one `>` (one tag as long as the document) needs 512 MB, as does one tag of bare words; `<a ` repeated and closed 256 MB; `<item a= a= ...>` 256 MB; one tag with 190,000 quoted attributes 128 MB; 500,000 empty elements 96 MB. (Without a `>` anywhere the parser gives up at once, which hides the problem.) Through `parseFeed`, at 1 MB: all of those are refused by the shape check at 16 MB. Tags of 8 KB that the check lets through, filled with bare words, slashes, tabs or 64 `a=` and padding, are thrown out by the parser itself at 16 to 24 MB. The second review found that one run of text was the costly shape the check let through: 1M two-byte characters in one run (reachable: 1 MB of byte 0x80 served as windows-1252 is 1M euro signs) failed at 64 MB and passed at 68 (CJK 60/64, ASCII 32/40), while the same text in runs of 128K passed at 24 and a 1 MB CDATA section at 16. Hence `MAX_TEXT_RUN`; one long run, and runs joined only by comments, are now refused. Shapes that parse, re-measured in the final round of task 7 (`parseFeed` alone in Node 22.14, the input built in the same process, each shape checked to come back as a feed with its one item, caps 64 down to 8 MB in 4 MB steps, two runs each; the smallest cap that passed both): 59,000 elements with distinct names filling 1 MB 28 MB (fails at 24) with a process maximum RSS of 145 MB, the worst found; 1 MB of the longest text runs (8 runs, 7 of them 131,072 long, split by `<b/>`) 20 MB in euro signs or CJK (fails at 16; RSS 129 MB), 16 MB in ASCII, in `&amp;` references or in `>`; 59,000 one-character text nodes, 59,000 elements of 1 MB with one name, 2,000 elements of 64 attributes and 59,000 tags nested 57 deep 16 MB; 59,000 text nodes of 13 characters and 29,500 open and close pairs 20 MB; 59,000 empty `<a/>` (236 KB) 12 MB; a 1 MB CDATA section of euro signs and 1 MB of comments 8 MB, the lowest tried, where a tiny feed also passes (RSS 86 to 91 MB). These come out lower than the earlier round's figures for the same shapes (it had 59,000 empty elements at 40 MB and a tiny feed at 16), whose harness is not recorded; the earlier figures are replaced, not confirmed. Old space is not the whole heap, so read the worst accepted feed as about 30 to 60 MB (its RSS is about 60 MB over the tiny feed's). An earlier round also ran 2,400 random markup-like documents of 1 MB under a 64 MB cap (the 391 that passed the shape check all parsed or were refused by the parser without running out); that was not repeated with the new limits. Page reader: HTMLRewriter is native, so only workerd's whole-process RSS can be sampled, which also holds garbage not yet collected: idle 107 to 111 MB, after one scan of a hostile 2 MB page 119 to 140 MB for most shapes and 175 MB for 200,000 headings inside one link. That page scanned 3 and 30 times in a row gave 199 and 210 MB, and six scans at once (what `/v1/feed` can run) 208 MB, so the figure does not grow with the number of scans and is mostly garbage waiting to be collected; what our code keeps per page is bounded by the counts above. This has not been checked on a deployed Worker, where the limit is real. Calendar path (`parseCalendar`, 2 MB, measured in Node the same way; not changed in task 7): 83,000 EXDATE lines on one event need 112 MB of old space, 233,000 nested `BEGIN:X` lines 96 MB (then refused), 28,000 small events 56 MB, the other seven shapes tried 16 to 64 MB. So the calendar route can exceed a Worker's memory on a hostile 2 MB file and needs its own task.
