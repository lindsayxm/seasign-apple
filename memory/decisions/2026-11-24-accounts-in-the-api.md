# 2026-11-24: accounts in the API (task 13), the entitlement check (task 221), and how phase B is split

Decisions of the lead during tasks 13 and 221, after security reviews. The user has been told; none is the user's own wording. Details of the code are in `memory/architecture.md` ("Accounts in the API (task 13)", "Entitlements in the API (task 221)").

- **An account is Apple's `sub`, never an email.** Better Auth's `user.email` is a synthetic value made from the sub (`accountEmail(sub)`, `...@apple.seasign.invalid`), never shown and never used to look anyone up; the real Apple email is kept in `user.apple_email` from the first token that carries one, for contact only. Account linking is off. Reason: with Better Auth's defaults a second Apple account presenting the same verified email was signed in as the first user (the reviewer ran it). Rejected: linking off with the real email in `user.email`, because the unique email column would lock the second person out.
- **`/api/auth/*` is an allow-list:** sign-in with an Apple identity token, get-session, sign-out; everything else is 404. The 64 KB body cap and a per-address rate limit (`RATE_LIMIT_AUTH`, 20 a minute) apply. Cookies are ignored both ways; only the signed bearer token (`set-auth-token`) authenticates. Reason: a sign-in with no token wrote a database row before failing, with no cap or limit, and the library exposes endpoints the app does not use.
- **A half-made user is deleted at that Apple ID's next verified sign-in** (`removeHalfMadeUser`). Reason: the adapter writes user and account as two inserts with no transaction, and a failure between them locked that Apple ID out for good. Consequence for later tasks: never leave a `user` row without its `account` row.
- **Nothing of Apple's is stored but the sub and the email:** no Apple tokens, no IP address; the User-Agent is cut to 256 characters.
- **No secret default:** without `BETTER_AUTH_SECRET` (32 characters or more) the auth routes answer 503. The user sets it for local dev and for production; the agent never sees it.
- **Phase B is split** into tasks 13 (done), 221 (entitlement record and check), 222 (sync), 223 (account deletion), 224 (`/v1/discover` requires an active entitlement), 225 (Cron refresh), with follow-ups in 226.
- **The server's entitlement check fails closed** (task 221): active only for the state `active` with an expiry later than now and no revocation; grace period, billing retry, no row, an unknown state or a missing expiry are not active (403 `subscription_required`); a read error is 503 `entitlement_unavailable`, which the phone should treat as its Unknown state, never as allowed. One Apple subscription (original transaction ID) belongs to one account and is never reassigned.
- **The purchase is linked to the account after sign-in, not by the purchase carrying the account's ID.** The plan's phase B item 2 says the purchase carries the account's ID, but the approved flow is purchase first, then sign-in, so no account exists at purchase time.

Open with the user: how the server verifies Apple's purchase data (the lead recommends the App Store Server API with a key the user sets, over validating the certificate chain in the Worker: it also returns the current status, so a receipt from before a refund cannot be recorded as active); whether a sandbox purchase counts on the production server (App Review buys in the sandbox); session length (7 days sliding today, the lead suggests 90); whether account deletion revokes Sign in with Apple access automatically (needs a Sign in with Apple key as a secret) or tells the person how to do it.
